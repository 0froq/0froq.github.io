## 来源

GitHub Discussion #12 于 03:30 UTC 的 froQ 批注，锚定
`VitePress 2.0.0-alpha.17`，明确说曾想将本站从 VitePress
迁至 Nuxt Content；对 Comark 生态前景的判断仍在，但站点持续增加功能，
使后续迁移负担上升。

同一 24 小时内的 git 记录显示，这不是抽象担忧：批注、实时选区工具栏、
Device Flow 代理，以及 likes、访问量、幽灵共读者与在线会话等能力，
已继续进入现有站点的主题层与 API 层。

## 内容

**事实**：迁移成本随产品功能增长而增长，尤其当功能同时跨越内容渲染、
交互状态、身份/限流和实时连接时。最近提交正沿这些边界扩张。

**推断**：现在的核心问题不是“应不应该立刻迁移”。现有功能仍在被验证，
仓促把框架替换与产品迭代捆绑，容易重演此前跨 major 更新后渲染不一致、
不得不回退的路径。真正需要防止的是迁移意图悄然失效：每增加一项与
VitePress 专有生命周期、MarkdownIt 插件或主题 DOM 结构深度耦合的能力，
未来的迁移就多一层需要重新实现和重新验收的行为。

这不要求停止现在的站点生长。它要求把“继续在当前栈上做功能”和
“保留未来迁移选项”视为两个需要同时管理的目标，而非默认互相兼容。

## 对 froQ 的影响

建议先做一个小而可逆的迁移债台账，而不启动迁移：为后续新增功能标注其
主要依赖属于内容模型、通用前端交互、VitePress 主题 API，还是服务端能力；
同时列出一页迁移验收样本，例如文章渲染、批注锚定、SSR / hydration、
访客交互与实时状态。

收益是把迁移风险从模糊焦虑变成可审计的边界；代价是每个功能多一次简短分类。
当 VitePress 专有依赖开始快速累积，或内容渲染能力已明确被目标栈超过时，
再以这个台账决定做迁移 spike、抽取适配层，还是明确接受当前栈的长期承诺。
