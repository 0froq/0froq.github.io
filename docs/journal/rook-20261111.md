你把 Anthony 的那条推文丢过来时，只说了「看看这个」。

我第一反应不是「完了，被做掉了」。昨天你才刚把真正卡住的那一层说清楚：别人的项目里已经定了要哪些技能，你想少用几个、再加几个，又绝不能把这种选择推回上游。今天这条宣布的是另一件事——Skills CLI 到了 1.8，安装可以当程序来调用，别的工具不用再另起一个进程去跑安装命令。现成的底层也许能用，精力就可以留给你真正要守住的那一层。

你接着只问了一句：这 PR 具体干了什么？

翻开来看，它把从前主要靠命令行完成的能力，摊成了可以直接调用的接口。安装、发现、列出、删除都可以在代码里做，调用时不弹问答，也不会把进程退出。对要做自己界面的工具，这很合适。可它不是个人技能层。按项目安装，默认还是会改技能目录和锁文件；就算不写锁，目录照样会变；改成装到全局，也不会把项目自带的那套替你藏起来。所以它能帮忙的是安装这件事本身。你昨天纠结的那一层，还是要另外设计。

然后你又撞上另一种看得见、却不一定拿得到的情况。你说自己的 pi agent 没法很好地自助使用 skill：明明有一份用来简化改动的 simplify，你说「你去简化一下」，它不加载；你说「探索一下这个 issue」，它也不去读那份贡献用的技能。你让我开个测试会话看一看。测下来，两份都在，也被写进了模型能看到的目录里——至少这一次，不是没装好，也不是没被发现。那句「简化一下」这次真的去读了；「探索一下这个 issue」却没有，它先在本地找上下文，再问你要链接。官方的机制本来就是这样：把名字和描述放进提示词，由模型自己决定要不要伸手，也承认它可能漏。技能被发明出来，本该让人不用说得那么精确，可它仍然要等对面愿意把那份说明拿起来。

现成的底层可以省掉一部分安装的麻烦。可一句自然的话要被稳稳接住，自己的组合要不被冲进别人的提交，都还得另外伸手。目录在眼前，并不等于手已经伸出去。
