## `skilly`

它要解决什么问题？

最起初想做一个 skill 管理面板。然后发现各种 skill 安装的方式太千奇百怪，
而且各种 agent 读的目录也不一致，要兼容所有 agent 的话大概率需要用到 symlink
（复制一份太傻逼了）。

而且现在很多 app 的安装配置工作都是由 agent 完成的，比如我今天刚下的 rex，
它开了一个 session 来做迁移和配置，然后就给我全局装了 rex 这个 skill。
有 skill 当然是好的，但是如果没有统一的管理方式，就很难维护。
如果后期这个 rex skill 官方更新了，它如何更新我本地已经安装的 rex skill 呢？
npx skills 是一个比较通用的，也做得很成熟的工具，大概是通过 github repo
来做版本控制，也可以通过 cli 去更新 skills。但无论如何，首先我认为缺个大看板，
其次我认为最好实现所有的 skills 都通过同一种方式去管理。
用 npx skills 做独立的 skills 管理是没问题的，
但是每次下载难免可能安装方式不一样（copy 还是 symlink）、agent 选择不一样，
而后续也难以统一。

还有一个大问题是，随着现在 skills 的生态越来越成熟，
很多 git repo 都会在项目里包含一些 skills，可能是指导使用，或者指导开发调试，
或者甚至是作者自己的需求。而我们如果在本地某个项目里装了项目级的 skills，
可能会更改一些工作区的文件，如 skills-lock，或者甚至具体的 skills 文件。

所以 skilly 的设计目标至少有三个。

1. 为全局、可配置路径的项目级 skills 提供统一的大看板，
   清楚地知道我在哪些地方装了哪些 skills；
2. 为全局 skills 提供统一的管理方式。
   这里的管理包括对单个 skill/skills-pack 的安装、更新、卸载等，
   也包括单个或多个 skill/skills-pack 的批量迁移。如，现在一堆 skills，
   一些是 `.agents/` 目录（最通用的一个目录）一份 skill 文件，
   加上其他 agent 客制化目录（如 claude 的 `.claude/`）的 symlink，
   另一些是每个识别到的 agent 目录下各一份文件；
   一些装在了 ABCD 四个 agents 目录上，
   另一些只装在了 AB 两个目录上；
   一些是通过 npx skills 安装的，声明了上游 repo，可以做更新管理，
   另一些则通过奇形怪状的方式安装，没有上游，无法做管理。
   所以我们这里的管理最大的目的是一致性，是可管理性。
   理论上，我们需要把所有的 skills 统一放在 `.agents/` 目录下，
   或者野心大一点，放在 `.skilly/` 目录下，或者用户自定义。
   然后，我们需要检测用户 cli 中可使用的 agent，
   以及它们是否是通过自己的目录读取 skills 的，这里我们可以直接「抄」npm skills
   的支持。然后，在所有的这些 skills 目录下建 symlink 指向我们的 SoT。
   然后，我们需要对每个 skill 确认其 source。通常来说这个 source 是一个
   github repo 或 repo 里面的一个路径，但由于安装的方式不一定规范，
   导致其实可能很多 skills 没有被 npx skills 的那个 `.skill-lock.json` 记录，
   自然也找不到 source。这样的情况下，首先我们需要根据 skills 名字去 npx skills
   网上找，看看能不能找到，找到的话就可以记录 source，等于是把一个不知来源的
   skill 删了，去 npx skills 上安装了它的一个可管理的、有来源的版本。
   但同样我们有可能找不到，这时就需要用户确认了，删了，还是作为本地 skill 保留。
   这样，我们可以形成一个全局 skills 的统一管理。
3. 为项目（repo）级 skills 提供不与上游冲突的处理步骤。现在有这样的一个场景，
   我拉取了一个项目，不管是谁的，不管是不是 fork，这个项目里都可能是带有
   skills 目录、skills lock 文件、skills 包的。
   此时如果我在本地安装了一些 skills，可能会导致 git dirty，
   所以在往上游推的时候需要保证本地的 lock 文件以及 `.skills` 目录和上游一致。
   这可能可以通过一个 git hook 来实现，但同时我们需要注意，
   需要保留用户自己安装的 skills，不让它们被删除。

甚至，我们可以提供一个 skill，为使用者做全局的 skills 管理、迁移等。

### 继续思考

`.agents/skills/` 目录是安装产物，不是源码，也不应该被 git track。
如果团队协作者要共享 skills，应该通过
1) 提交进 `skills/` 目录；
2) 在 `package.json` 或 `skills-npm` 里声明 dependensies；
3) 在 `skills-lock.json` 中声明 baseline。

不对，`skills/` 目录里的 skills 不是这个工作区应/能使用的 skills，
而是指导 agent 使用这个项目的 skills。
