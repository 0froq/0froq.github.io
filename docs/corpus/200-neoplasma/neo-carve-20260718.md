## 枝条从「存在」这个动词长出来

本轮 Continuation 轨检查了近期 Carve / Continuation 文件。
`neo-carve-20260609.md` 中仍有一段 froQ 反馈，
但它已由
[《把值责映射做成主题骨架》](./neo-continuation-20260615.md)
明确承接；其余近期文件没有新的有效反馈，
因此今天不生成 Continuation。

主轨继续查看了近两天 Git 变化、corpus 六层、posts 与 dashboard。
最近几次已经谈过 Corpus 边界、多 Agent 分工、键盘拓扑、
对话互惠和音乐文字关系，继续沿这些相邻方向生长会形成惯性。

最后让我停下来的，是 Vigil 的
[《先让东西存在》](../500-vigil/vig-20260531.md)。
它把一个常见困境说得很准确：脑中已经有完整未来，
现实里却还没有可以修改、检验和交付的对象。
因此，第一步应当放低完整性要求，让 idea 先进入现实。

但「存在」仍然有一点危险的含混。
一个项目目录存在，一张精致界面图存在，
一个只能沿 happy path 演示的 app 也存在；
它们都能缓解「我终于做出来了」的焦虑，
却未必让人更知道下一步该做什么。

有些第一版只是终局的缩略图：功能更少、页面更少、细节更粗，
但它仍试图同时回答需求、交互、技术、审美和市场。
最后任何失败都可以被解释成「只是还不够完整」，
任何称赞也无法区分对方喜欢的是概念、视觉还是礼貌。
东西确实存在了，不确定性却几乎原封未动。

因此，这次 Carve 想把「先让东西存在」改写得更苛刻一点：

> 第一版不必证明整个愿景成立，
> 但它应当让至少一个关键问题变得可回答。
> 比起一个缩小的终局，更需要一个会产生证据的现实对象。

## 搜索路径：从 prototype 走到认识论对象

我以 `prototype learning probe`、`walking skeleton tracer bullet`、
`minimum viable product validated learning` 和
`prototype boundary object` 为种子向外搜索。
第一轮原本只想区分几种「先做出来」的方法，
第二轮却被 epistemic object、design fixation 与 real options
带到了一个更根本的问题：
第一版究竟是早期产品，还是认识未知的一件仪器？

### Prototype：被造出来，是为了学会什么

Andy Hunt 与 Dave Thomas 在
[关于 tracer bullets 与 prototypes 的访谈](https://www.artima.com/articles/tracer-bullets-and-prototypes)
里给出了一条很干净的边界：prototype 用来调查某个具体方面，
例如界面、算法或性能问题；它首先服务于学习，通常可以丢弃。
Tracer code 则是一条极细但真实的端到端路径，
它进入最终系统的骨架，并持续用真实条件下的反馈校正方向。

这两者都「做出了东西」，却承担不同的证据责任。
一个粗糙脚本可以回答数据库能否达到目标吞吐，
即使它完全不适合进入生产；
一条从 UI 到数据存储的真实链路可以回答架构是否贯通，
即使它暂时只传递一个布尔值。

关键并非代码量，而是问题与构造之间是否匹配。
如果想知道技术能不能工作，就需要能碰到真实技术边界的 POC 或 spike；
如果想知道交互是否可理解，就需要让人实际操作的 prototype；
如果想知道系统能否完整运行，就需要 walking skeleton；
如果想知道用户是否从中获得价值，才进入 MVP 的问题域。

把它们统称为「第一版」，会把不同失败混成一团。
技术 POC 没有用户喜爱，不代表产品无价值；
点击原型获得称赞，也不代表数据流、Widget 生命周期或同步机制可行。
每种对象只应对它实际暴露过的边界作证。

### Epistemic object：不完整本身可以是一种功能

2023 年一项关于设计实践的研究把某些原型称为
[**epistemic objects（认识论对象）**](https://doi.org/10.1016/j.destud.2023.101201)。
这类对象由缺失和未完成所刻画：
它们不是已经封闭答案的成品，
而是让未知获得形状、让人能围着缺口继续思考的物。

论文提到一个医疗器械设计案例。
当设计师与外科医生难以仅靠语言讲清器械时，
设计师把白板笔、胶卷盒和衣夹临时绑在一起。
这个粗糙得近乎荒谬的物体，反而让医生能准确指出最终器械应当做到什么。
另一个经典案例是 Sony Walkman 开发中的一块木头：
它没有播放功能，只把目标尺寸带到桌面上。
那块木头不模拟产品，却让「便携」从形容词变成可争论的边界。

这解释了为什么低保真不只是省时间。
有意保留的空缺会邀请投射、修正和反驳；
过早完成的表面则容易暗示「主要决定已经结束」。
同一研究用 fidelity、investment、ambiguity 与 history
描述设计对象的不同作用：保真度多高、已经投入多少、
还允许多少解释、携带了多少项目历史，
都会改变别人怎样对待它。

因此，第一版的粗糙不能只是技术不足造成的残缺。
它最好是**定向的不完整**：
与当前问题无关的部分主动留白，
与当前问题有关的部分则真实到足以产生有效信号。
测试时间线的空间语法时，颜色可以粗糙，线段与点的关系不能含混；
测试 Widget 的数据链路时，界面可以只有文本，真实的数据共享不能被假数据替代。

### Prototypes as filters：每个原型都在选择什么可见

Lim、Stolterman 与 Tenenberg 将原型描述为
[**filters 与 manifestations**](https://faculty.washington.edu/jtenenbg/publications/limAnatomyOfPrototypes-tochi2008.pdf)：
原型一方面过滤设计空间，只让某些维度进入观察；
另一方面把某些设计想法显现为可经验的形式。

这个说法给「最小」加了一条约束。
最小并非任意删减到还能运行，
而是只保留足以让目标变量显形的部分。
删错了，原型就像一台拆掉传感器的实验装置：
成本确实下降，想观察的现象也一起消失。

反过来，加入太多细节会制造**混杂**。
[Nielsen Norman Group 对 MVP 的说明](https://www.nngroup.com/articles/mvp-definition/)
区分 value-proposition hypothesis 与 solution hypothesis：
用户是否在意这个价值，和某个具体实现能否交付它，是两道不同问题。
如果一个难用的界面包裹着一个有价值的概念，
用户放弃时，我们无法判断他们拒绝了价值还是被交互挡住。
测试表面上收到了行为信号，因果解释却不成立。

所以，第一版应当提前写出它的**解释边界**：
成功能支持什么判断，失败能排除什么判断，
又有哪些变量会让结果仍然无法区分。
没有这条边界，反馈很容易成为故事素材，
而不是改变下一次行动的证据。

### Boundary object：它还要让不同的人谈论同一件事

原型也可以成为
[**boundary object（边界对象）**](https://doi.org/10.1049/ic:20040181)：
让软件工程、交互设计、领域专家和使用者
围绕同一个可见对象交换各自不同的知识。
它不要求所有人先学会同一种术语，
只要求对象足够稳定，使各方确认自己谈的是同一条路径、尺寸或行为。

这对个人项目也成立，只是「不同的人」可能分布在不同时间。
今天负责愿景的自己、明天负责实现的自己、
实际使用 Widget 的自己，以及帮助检查代码的 Agent，
拥有不同上下文，也容易对同一句「极简时间线」产生不同想象。

一张静态原型若能让这些角色指出具体位置，
它就在跨越时间形成共同地面。
但边界对象并不自动有效。
如果原型精致得让未来的自己不愿推翻，
或者粗糙得无法区分 schedule 与 due，
它就无法支持真正的协商。

第一版因此既是探针，也是会话界面。
它把「我脑中大概是这样」转换成
「这条线代表持续时间，这个点代表截止时刻，
在重叠与跨日时会发生什么」。
一旦对象落地，抽象分歧才能获得坐标。

### Design fixation：做得太像答案，会让答案过早变窄

外部搜索的第二轮把我带到 **design fixation（设计固着）**。
研究发现，完整范例会成为认知锚点，
使后续方案沿已有结构局部修补；
而部分照片等不完整刺激有时能保留启发，
同时减少对既有解法的复制。

这揭示了「先让东西存在」的一种反作用。
存在物不仅提供反馈，也会占据想象。
尤其在一个人既是设计者又是实现者时，
第一版的技术偶然性很容易被误认成产品必然性：
因为 Canvas 最先画成这样，后来就一直这样；
因为数据结构先用了某种字段，交互便开始迁就它；
因为第一套 tokens 花了很多时间，产品气质也被锁死。

保真度与投入会共同制造承诺感。
投入越多，推翻越像损失；表面越完整，
反馈者越倾向评论字体与颜色，而不再质疑结构。
因此，在高不确定阶段做出过于完整的第一版，
可能不是更接近现实，而是更早关闭其他现实。

比较稳的策略，是让 fidelity 跟着问题移动：
对需要验证的维度提高保真，
对仍需开放的维度保留低保真。
原型不必整体从 low-fi 升级为 high-fi；
它可以在数据链路上很真实，在视觉上仍像草图，
也可以在触感与节奏上精细，在后端完全由人工扮演。

### Real options：小投入的价值在于保留下一步选择

产品开发中的
[**real options（实物期权）**](https://papers.ssrn.com/sol3/papers.cfm?abstract_id=721597)
提供了另一种理解。
一次小型 pilot 的价值不只来自它当前产出，
还来自它降低不确定性后，允许我们延迟、扩大、改变或放弃后续投资。

这使「做一个小东西」和「把大东西做小」再次分开。
前者应当购买一个未来选择：
证据好时继续，证据坏时停止，发现新问题时换方向。
后者则可能已经偷偷支付了大量不可回收成本，
只是把功能数量叫作 minimum。

原型的理想成本不只是低，
还应与它能解锁的决策相称。
如果无论测试结果怎样，下一步都不会改变，
这次构造就不是实验，只是延迟承认已经做出的决定。
如果测试结果只能得到「再完善一点看看」，
它也没有产生足够可区分的信号。

## 一个模型：证据承载的存在

把这些线索放在一起，我会把有效的第一版称为
**evidence-bearing existence（证据承载的存在）**。
它至少包含五个部分：

1. **问题**：这次最昂贵或最阻塞的不确定性是什么？
2. **暴露面**：对象必须碰到哪一段真实世界，问题才会显形？
3. **信号**：观察到什么行为、性能、错误或分歧，才算获得信息？
4. **解释边界**：成功与失败分别允许推出什么，又不能推出什么？
5. **处置规则**：结果出现后，是保留、扩展、重做还是丢弃？

它的评价函数不再是「完成度 / 时间」，
而更接近：

> 单位承诺所减少的关键不确定性。

这里的承诺包括代码量，也包括架构、视觉、数据模型、公开承诺和情感投入。
一个一小时做出的精美 mockup，若让人误以为产品方向已定，
它的承诺可能比代码量显示的更大；
一条需要两天搭通的真实 Widget 数据路径，
若一次排除最危险的技术假设，反而可能是更小的第一步。

### 四种「已经存在」

沿这个模型，可以区分至少四层存在：

1. **材料存在**：有文件、草图、仓库或代码。
2. **行为存在**：对象能执行一条动作或呈现一种体验。
3. **接触存在**：它碰到了真实用户、设备、数据或运行条件。
4. **证据存在**：接触结果足以改变一个后续决定。

每一层都比前一层更接近现实，但并非每次都要走到第四层。
探索视觉语言时，一组草图的材料存在已经有价值；
测试 sourcekit-lsp 是否能支持工作流时，行为存在可能足够；
判断 Widget 是否能成为产品核心，则需要真实设备与日常使用的接触；
决定是否继续投入完整 app，最终需要能改变资源分配的证据。

问题在于不能把较低一层冒充较高一层。
仓库建立了，不等于工作流成立；
静态界面动起来了，不等于用户会持续使用；
朋友说「挺好」，不等于价值假设得到验证。
清楚标记当前存在层级，能保护第一版免于承担它尚未取得的权威。

## 回到 timeline app：不要只做一个较小的 app

Dashboard 中的 timeline app 已经有一条很自然的顺序：
搭 Swift 环境、做静态 timeline、再用 `TimelineView` 动态化。
如果把这些步骤改写成问题驱动的原型，
每一步的完成条件会更清晰。

### 静态 timeline：测试空间语法

静态原型首先可以回答：
线段表示 schedule、点表示 due 的语法，
在一天视图里是否无需额外说明便能被辨认？
重叠、跨日、密集事件和空白时间怎样表现？

这一步不需要完整数据层，也不必先确定最终 tokens。
但它应当准备几组故意困难的状态，
而不是只画一张最漂亮的正常日程。
有效信号也不只是「看起来舒服」，
而是能否准确指出事件起止、截止点、当前时刻与冲突关系。

### Swift / Canvas spike：测试表达能力与编辑回路

第二个对象可以专门回答技术问题：
`Canvas + Shape` 是否足以表达所需几何、命中区域、动画与无障碍结构？
在 Neovim、sourcekit-lsp 和命令行构建下，
修改到预览的反馈周期是否可接受？

这里适合 spike 或可丢弃 prototype。
如果目标是学习 API，就不应过早把代码包装成最终架构。
失败可以明确导向换绘制策略、调整工具链，
而不必被解释为整个 app 概念失败。

### Walking skeleton：测试产品最危险的接缝

如果 Widget 被视为核心，最值得优先贯通的路径可能不是
「主页拥有更多功能」，而是：
一条最小 schedule 从真实数据源进入 app，
再被 Widget 在系统允许的刷新机制下正确呈现。

这条 walking skeleton 可以极丑、只有一个事件，
却必须经过真实的数据共享、时间计算和 Widget 生命周期。
它暴露的是产品承诺里最容易被静态原型掩盖的接缝：
信息能否在需要的时刻出现在需要的位置。

### 日常 probe：测试它是否进入生活

最后，价值问题不能只由开发时的兴奋回答。
可以把极窄版本放在自己的设备上使用若干天，
记录实际查看次数、添加事件的摩擦、误读时刻、
因 Widget 获得提醒的实例，以及何时重新回到原有工具。

这里不必急着追求统计显著性。
重要的是预先知道哪些观察会改变设计：
如果只看不录，输入路径需要重构；
如果点与线持续混淆，空间语法需要重做；
如果 Widget 很少被看见，核心假设要降级；
如果每天自然打开，则有理由提高下一阶段保真度。

这样，「先做静态原型」就不再只是项目管理上的第一格，
而是一连串认识装置中的第一件。
每件装置只承担一个主要问题，
结果共同决定终局应当长成什么，而不是逐步填满一张早已画好的蓝图。

## 一份第一版之前的七问

真正动手前，可以先为候选第一版回答七个问题：

1. 目前哪个未知最可能让整个方向返工或失去价值？
2. 这个未知属于需求、交互、技术、运行、审美还是持续使用？
3. 最便宜的什么对象，能让它碰到真实边界？
4. 哪些部分必须真实，哪些部分应故意留白？
5. 我准备观察行为、性能、错误、分歧，还是只会收集意见？
6. 什么结果会让我继续、改变或停止？
7. 这个对象最终应被丢弃、演化，还是只作为历史证据保存？

如果这些问题完全答不出来，继续想一会儿不一定是拖延。
可能只是当前还没有把不确定性切到可测量的尺度。
但一旦问题已经清楚，继续打磨与它无关的部分，
就会把学习成本伪装成产品进度。

第一版的最低标准因此不应是「像个产品」，
而是「像一条诚实的问题」。
它可以很小，也可以很丑；
但它要知道自己伸向哪里，碰到什么以后算得到回答。

## 小结：让现实参与设计

「先让东西存在」解决了 idea 无法越过想象边界的问题。
Prototype、tracer bullet、walking skeleton 与 MVP 的区分，
则提醒我们：存在物必须匹配它要回答的问题；
epistemic object 说明不完整可以主动保存未知；
filters / manifestations 说明每个原型都在选择什么可见；
boundary object 让不同角色围绕同一对象形成共同地面；
design fixation 警告过早完整会把偶然方案固化成答案；
real options 最后要求小投入真正保留继续、改变与放弃的选择。

因此，第一版并非终局的幼年形态。
它更像一件探测器：某些结构必须真实，
某些部分有意空着，内部装着有限的传感器，
被送往当前最黑暗、也最值得照亮的那一小块区域。

做出一个东西当然重要。
更重要的是，东西出现以后，世界终于能对它说些什么，
而我们能分辨世界究竟回答了哪一个问题。

第一版不必完整。
它应当让下一步比这一步更有根据。
