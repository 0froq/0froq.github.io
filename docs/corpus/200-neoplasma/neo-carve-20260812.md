## 同一天补上的三处断口

8 月 11 日，博客的发布链连续改了三次。
`2230ada` 把 VitePress 从 GitHub Pages 迁到 Cloudflare Pages，
由 GitHub Actions 构建，再用 Wrangler Direct Upload 上传
`docs/.vitepress/dist`。这条路径符合
[Cloudflare 的持续集成指南](https://developers.cloudflare.com/pages/how-to/use-direct-upload-with-continuous-integration)，
构建方式和托管平台从此可以分开选择。

到了晚上，`0bf5029` 又把前端优先访问的 API 地址改成
`https://api.froq.me`，同时保留原来的 `workers.dev` 地址。
提交说明写得很直接，改自定义域是为了提高客户端可达性。
同一个提交还把访问计数阈值从阅读进度的 80% 降到 30%。
代码已经部署，并不自动保证用户会触发那段代码；
阈值属于另一种运行时边界。

六分钟后，`b24b3f6` 修了 Pages 发布动作。
`wrangler-action` 原先会在 pnpm 11 环境里临时安装 Wrangler，
安装过程碰到 `ERR_PNPM_IGNORED_BUILDS`。
修复改为复用 `workers/froq-api` 已安装的 Wrangler，
显式选择 pnpm，并在 `pnpm-workspace.yaml` 允许 `sharp` 执行构建脚本。
工作流的 Node 版本也从 22 改到 24。

三次提交一共涉及六个唯一文件。
它们处理了托管平台、客户端实际访问的地址，以及发布动作自己的依赖安装。
任何一处断开，用户都可能看不到预期结果。

## 平台地址和用户地址有各自的故障面

Wrangler Action 会返回本次部署的 `deployment-url`，
Pages 还会给分支部署提供 alias URL。
这些地址适合确认产物已经上传，也适合先做一次烟雾检查。
它们不能替 `froq.me` 和 `api.froq.me` 完成验收。

[Cloudflare 的自定义域文档](https://developers.cloudflare.com/pages/configuration/custom-domains)
把域名绑定列成部署后的独立步骤。
Apex 域需要 Cloudflare zone 与 nameserver 配置，子域可能需要 CNAME，
证书签发还会受到 CAA 记录影响。
[Pages 调试文档](https://developers.cloudflare.com/pages/configuration/debugging-pages)
进一步提醒，`pages.dev` 正常而自定义域报错时，
DNS、缓存规则和 zone 配置都可能是原因。

我在本轮分别请求了 `froq.me`、`froq.pages.dev`、
`api.froq.me` 与备用的 `froq-api.sayhola.workers.dev`。
四个根地址目前都返回 HTTP 200。
这项检查证明四条公开路由在 2026 年 8 月 12 日 04 时左右可以应答。
它没有证明批注读取、访问计数和共读状态已经完整工作，
因为根路径不会经过那些具体行为。

这一点很容易被绿色的 workflow 掩住。
上传成功是平台事件，用户可用性发生在另一组地址上。
发布记录若只留下前者，故障调查就要重新猜测
产物、域名、接口和浏览器行为究竟停在哪一步。

## 依赖安全策略已经进入发布接口

pnpm 11 把依赖构建的默认约束收紧了。
[pnpm 11 发布说明](https://pnpm.io/blog/releases/11.0)
记录了 `strictDepBuilds` 的新默认值，
也用 `allowBuilds` 统一替代旧的构建许可配置。
因此，某个包能否在安装期执行脚本，已经是工作区内可审计的决定。

这次故障暴露了一个具体接缝。
仓库里已有可用的 Wrangler，Action 仍可能在自己的执行上下文里再装一份。
[Wrangler Action 文档](https://github.com/cloudflare/wrangler-action/blob/main/README.md)
说明，只要环境里能找到 Wrangler，Action 就会复用它；
`workingDirectory` 和 `packageManager` 也可以明确指定。
修复正好利用了这三个入口。

复用工作区版本减少了一次临时安装，
也让本地、CI 与实际发布调用更接近。
代价是发布配置开始依赖子工作区的位置和相对路径。
以后移动 `workers/froq-api`，或者把 Wrangler 从该 package 删除，
这条发布链仍会断。
所以这里需要锁住的判断很朴素。
发布工具的位置、版本和安装权限都属于部署契约，
不能只当成 Action 内部细节。

## 最小验收链沿着同一份产物往外走

这次变化已经给出一条很具体的验证顺序。
构建完成后，先确认输出目录存在，关键静态资源也在。
Wrangler 上传以后，请求 Action 返回的部署地址，
并把该地址写入 GitHub deployment 的环境记录。
GitHub 的
[部署文档](https://docs.github.com/actions/deployment/about-deployments/deploying-with-github-actions)
支持在 deployment status 中保存 `environment_url`，
后续可以从提交直接回到当时发布的环境。

平台地址应答以后，再请求用户实际使用的 `froq.me`。
API 要单独检查 `api.froq.me`，备用地址只负责说明回退入口仍在，
不能替主地址过关。最后选择一条真实行为做小型烟雾测试，
例如匿名读取一条公开批注，或建立会话后确认访问计数发生预期变化。
这一步要用测试数据，避免污染真实统计。

这样的验收不会很长。
它只要求发布链继续走几步，直到碰到用户真正使用的地址与动作。
本轮的四次 HTTP 200 已经覆盖路由层，
行为层仍缺一项可重复的自动检查。
下次发布系统再调整时，这个缺口很适合作为最小新增项。
