## 那条候选判断需要重新核对

8 月 15 日的
[Inbox 记录](../200-neoplasma/neo-inbox-2026-08-15.md)
留下了一个很具体的猜想。Hermes 新发布的 Bot Mode
若能拆分任务，也许可以代替正在试用的 Multica。
当时的文档核对没有找到对应入口，只确认了 Hermes 已有
`delegate_task` 与 Kanban，于是把 Bot Mode 的能力记为未知。

这份判断很快过时了。
Teknium 在 8 月 13 日公开的
[发布帖](https://x.com/Teknium/status/2088003994904113614)
给出了实际仓库。Bot Mode 是一天期公开测试中的
Hermes Desktop 插件，随后会根据反馈进入主桌面端。
它把每个 Hermes profile 显示成一个 bot，
给它名称、职责说明、头像和独立聊天，bot 之间还能传递消息。

这次搜索的第一轮缺口也由此暴露出来。
只查 Hermes 主文档里的同名词，会先撞上 WhatsApp 的 bot mode，
两个功能恰好共用名称。把关键词改成仓库名与 Agent Inbox 后，
才找到真正对应 froQ 所见功能的
[Hermes Bot Mode 仓库](https://github.com/NousResearch/Hermes-Bot-Mode)。
候选本身确实存在，问题转为它承担了哪一层工作。

## Bot Mode 把 profile 组织成了一支可见的队伍

仓库对实现边界写得很清楚。一个 bot 就是一个 Hermes profile。
它拥有独立的配置、记忆、技能、凭据和聊天历史，
Bot Mode 在这些既有对象上加了一层桌面交互。
创建与编辑调用 profile RPC，定时 routine 仍是 Hermes cron，
跨 bot 消息则通过命令行启动目标 profile 的
`Agent Inbox` 会话。

这里最有价值的变化发生在人怎样看待 agent。
普通 session 列表按对话排列，今天的研究和明天的代码审查
可能都混在同一个身份下。Bot Mode 固定了成员名单。
研究员、审稿人和执行者各自保留职责、记忆与入口，
人可以直接进入某个成员的长期聊天，也可以在当前聊天里
用 `@researcher` 发起一次交接。

它还提供了一个稳定的收件位置。
每个 bot 都有持久的 Agent Inbox，消息带来源归属，
接收者下一次运行时能读到它。
这比父 agent 临时生成匿名子代理更适合长期角色关系。
Hermes 官方的
[profile 文档](https://hermes-agent.nousresearch.com/docs/user-guide/profiles)
也确认了隔离范围，profile 分开保存配置、memory、sessions、skills、
cron 与 state database。

这份隔离仍有明确边界。profile 不等于 sandbox，
本机 profile 默认拥有同一用户的文件访问能力。
Bot Mode 的跨 bot 传话也是一次新的 CLI 调用，
仓库明确写着它目前不能中断一个正在运行的 bot。
它解决了成员身份、固定聊天和直接交接，
还没有把一项工作从提出到验收的全部状态装进去。

## Multica 保存的是工作经过，不只保存成员

第二轮搜索因此从 agent roster 转向 durable task lifecycle。
[Multica 的公开说明](https://multica.ai/)
把核心对象放在 project、issue、task 与 runtime 上。
Issue 保存目标、讨论、负责人和最终状态，
每次 agent 执行再生成一条 task，记录触发原因、进度与结果。
本机 CLI 也能直接列出项目、issue、运行记录与 run messages，
失败后可以用 `rerun` 重新入队。

这层结构带来一个关键性质。
某个 agent 会话可以关闭，任务仍然知道自己排队中、运行中、
被阻塞、完成或失败。后来接手的人也能从 issue 评论与运行记录
恢复上下文。Multica 还能把 Codex、Hermes、Pi、OpenCode 等
不同 runtime 放进同一工作区，由 daemon 领取任务并回报状态。
这些能力属于项目管理控制面。

Bot Mode 当前的 routine 与 Agent Inbox 无法自然替代这张表。
cron 能按时间唤醒一个 bot，却不记录父任务是否完成。
Agent Inbox 能传话，却没有统一的待办列、依赖边和失败重试状态。
一串聊天可以叙述工作经过，机器很难可靠地据此判断
哪个结果已经验收，哪个阻塞仍需人处理。

因此，Bot Mode 单独接替 Multica 会丢掉一部分可恢复性。
它已经有成员、有固定座位，也能互相喊人，
任务本身还缺少一份独立于聊天的生命史。

## Hermes Kanban 才是替代判断中的另一半

Hermes 自己已经有这块结构。
官方
[Kanban 文档](https://hermes-agent.nousresearch.com/docs/user-guide/features/kanban)
把它定义为 profile 之间共享的持久任务板。
任务保存在 SQLite，带负责人、状态、评论和父子依赖；
dispatcher 负责领取、启动 profile、回收崩溃进程与再次调度。
人也能在任意阶段评论、解除阻塞或交给另一角色。

它和 `delegate_task` 的差别也很适合这次判断。
`delegate_task` 是一次调用，父 agent 等子代理返回。
Kanban 保存一条可恢复的工作记录，执行进程退出后仍然存在。
Bot Mode 提供成员名单与聊天入口，Kanban 提供任务状态与交接证据，
两者组合后才接近 Multica 当前承担的职责。

组合仍然留有差异。
Hermes Kanban 的官方边界是单机，worker 是本机 profile 进程。
Multica 可以连接多台机器与多种 coding runtime，
并把 project、issue、agent 与团队活动放在同一工作区。
如果需求集中在一台 Mac、少数 Hermes profile 和个人使用，
Hermes 的本地组合会更短，也更容易沿用现有技能、记忆与 cron。
如果需要跨 runtime 调度、多人协作或多机执行，
Multica 的控制面仍然覆盖得更完整。

## 替代与否可以用一条真实任务验证

这项选择暂时不需要靠功能清单决定。
可以拿一条会经过研究、执行与审阅的真实任务做最小实验。
在 Hermes 中建立三个 profile，给同一项目开一个 Kanban board，
让研究任务与实现任务形成依赖，再由审稿 profile 给出通过或退回。
整个过程只允许 Bot Mode 负责找人和对话，
所有状态、评论、依赖与验收都必须落在 Kanban。

实验结束后只看几件实际结果。
中途重启 gateway 后任务能否继续，失败能否保留原因并重新调度，
审阅者能否只读任务记录就恢复上下文。
再比较 Multica 完成同一条链所需的人工操作，
以及两边是否都能追到最终文件和验证命令。

若 Hermes 组合能完成这些动作，froQ 当前的个人编排需求
可能已经不再需要第二套控制面。
若状态仍要靠聊天补叙，或非 Hermes runtime 仍频繁参与，
Multica 就还有清楚的保留理由。
