## 这次枝条从哪里长出来

近两天 Git 变化里有一个很小的动作：站点根容器的正文色从
`stone-700` 调成了 `stone-600`，暗色模式仍保持 `stone-400`。
旁边还有一整次 CSS quote / indentation normalization，表面上像格式化，
实质上像把主题系统重新梳了一遍毛流。

这个动作很小，但它碰到的是一个很大的设计变量：正文色。

正文色常被误认为「黑一点」或「灰一点」的品味问题。可是对一个以长文、
corpus、roadmap、代码片段共同组成的站点来说，它更接近页面的默认摩擦系数。
颜色太重，所有句子都在争夺前景；颜色太轻，阅读需要额外眯眼；层级没有余量，
标题、强调、链接、inline code 就只能靠更激烈的装饰来抢位置。

所以这次 Carve 不把 `stone-600` 当成一个单点数值，而是把它看成一个判断：
**默认文字不必永远站在最高音量，它应该给层级系统留下可用的响度余量。**

## 搜索路径：从 typographic color 到 role-based tokens

我用几个种子词向外探：`typographic color body text`、`APCA perceptual contrast`、
`semantic color tokens`、`visual hierarchy neutral text`。出来的线索有三组，
正好能把这个小改动放进更大的坐标系。

第一组是 **typographic color**。这里的 color 不是红蓝绿那种色相，而是文本块在页面上
形成的整体灰度、密度和重量。传统排版里，一段正文远看像一块有纹理的灰布：字重、
行高、行长、字距、前景色都会改变这块灰布的深浅。于是正文色并不只是可读性参数，
它还决定页面的「底噪」。底噪越重，标题和链接需要越高的响度才能穿出来；底噪越轻，
页面安静，但也更容易失去抓手。

第二组是 **APCA**，Accessible Perceptual Contrast Algorithm。APCA 用 `Lc` 表示
感知亮度对比，并且按用途给出阈值：长段正文需要更高对比，非正文内容可以稍低。
这比 WCAG 2.x 那种单一 contrast ratio 更接近真实阅读，因为同一个数值在浅色模式、
暗色模式、不同字重和字号下未必有同样的感知效果。APCA 文档里有一句很有用的提醒：
严格的 pass / fail 不能充分描述用户需求，因为对比需求本身会冲突，个性化仍然重要。
这意味着正文色不应只问「过不过线」，还要问「它承担的是哪一种阅读任务」。

第三组是 **role-based token / semantic token**。Carbon Design System 把 token 区分为
role 和 value：token 是角色，value 是在某个 theme 里的具体颜色。它还强调中性灰阶在界面里
承担 layering model，额外颜色要 sparingly and purposefully。Material Design 3 的颜色角色
也有类似逻辑：`surface`、`onSurface`、`onSurfaceVariant`、`outline` 等角色把背景、正文、
弱化文本和边界拆开。这里最值得带回站点的是：颜色不该只按色阶命名，至少在设计系统内部，
还要知道它在阅读关系里扮演什么角色。

这些线索合起来，给 `stone-700 → stone-600` 一个更准确的名字：它不是「把字调浅」，
而是把正文从最高对比文本降为默认阅读文本，把最高对比位置留给标题、strong、关键链接、
代码边界和危险状态。

## 一个判断：正文色是全站层级的基准音

如果把页面当成一段音乐，正文色不是某个装饰音，而是基准音。它一变，所有东西的相对响度
都会变。

当前站点的浅色根背景是 `stone-100`，正文从 `stone-700` 调到 `stone-600`。按 WCAG 2.x
粗略计算，`stone-700` on `stone-100` 约为 9.42:1，`stone-600` on `stone-100` 约为
6.99:1。也就是说，它从近似 AAA 余量退到仍高于 AA、接近 AAA 边界的位置。这个退让是有意义的：
正文仍可读，但视觉重量下降，页面整体会少一点硬边。

暗色模式是另一回事。`stone-400` on `stone-950` 约为 7.83:1，保留了比较充足的亮度。
这说明浅色和暗色不能机械对称：浅色模式里可以把黑度稍稍降下来，减少纸面刺感；暗色模式里
文字不能过暗，否则夜间阅读会变成雾里摸路。

这里可以形成一条站点设计原则：

> 正文色应是可长期阅读的默认层，不应占用最高强调层。

这条原则比「用 stone-600」更稳定。未来如果背景从 `stone-100` 改成更暖的纸色，
或者字体从霞鹜文楷 / 仿宋感切到另一套 serif，具体色阶可能要变；但角色不变：正文色负责
长时间承载，heading / strong / link / code 负责局部抬升，muted / meta / caption 负责退后。

## 可以长成 token 的四个层级

现在主题里已经有大量很克制的 stone 色阶：标题用 `stone-800 / stone-200`，strong 用
`stone-950 / stone-50`，inline code 用 `stone-600 / stone-400`，链接靠 dashed underline
和 document icon 提供非颜色提示。它其实已经有语义层级，只是还没有完全命名。

可以考虑把它们抽成四个阅读角色，而不是继续让所有组件直接记 stone 数字：

```txt
--text-body       长文默认阅读文本
--text-strong     标题、strong、关键断言
--text-muted      日期、说明、低优先级 meta
--text-link       链接与可跳转对象
--text-code       inline code / technical token
--border-subtle   低强度分隔线
--border-active   hover、focus、当前项
```

这不是要立刻重构代码。它更像给现有审美补一层语义骨架。
之后调色时，问题就不再是「这个地方要不要 `stone-700`」，而是：

- 这里是正文、强调、元信息，还是交互对象？
- 它需要 fluent reading、spot reading，还是只是可辨识的边界？
- 它在浅色和暗色下是否承担同一个角色？
- 颜色是否和字体大小、字重、underline、icon 一起构成层级，而不是独自承担层级？

这个问题方式更接近 Carbon 的 role-based token，也更符合这个站点的气质：主题色不大面积铺开，
只在 active、link、document hint 这样的少数状态里露出。中性灰阶负责空间，少量色相负责语义。

## 一个容易踩的坑：把安静误当成低对比

克制主题最容易犯的错，是把「安静」做成「看不清」。
`stone-600` 这次还没有掉进这个坑，因为它在浅色背景上仍有足够对比。
真正危险的是 metadata、caption、placeholder、disabled、border 这些次级层。
它们常常被设计成漂亮的浅灰，但里面如果有真实信息，就不能用接近装饰线的对比。

APCA 的提醒在这里很锋利：低于某些阈值的东西，对很多用户来说就等于不可见。
所以可以把站点里的低对比元素分成两类：

1. **有语义的信息**：日期、标签、目录项、说明文字、脚注入口。它们可以退后，
   但不能消失。
2. **纯结构的纹理**：分隔线、淡背景、装饰性 hover 底线。它们可以更轻，
   因为缺失时不损伤理解。

这条分界很重要。克制不是把所有东西都调灰，而是知道哪些东西必须被读到，
哪些东西只需要被感到。

## 一个很小的后续实验

如果要让这次 `stone-600` 不停留在一次手感调整，可以做一个很小的 specimen 页面，
不需要引入新框架，只放几组真实内容：

- 一段 corpus 正文，含 heading、strong、link、inline code。
- 一段 roadmap / log，含日期、标签、blockquote、列表。
- 一段 dashboard 样式信息，含 active、muted、border、hover。
- 一段代码块和 diff，检查技术文本有没有被正文色抢走。

然后只检查三件事：

1. 远看时，正文灰布是否均匀，标题是否自然浮出？
2. 近读 5 分钟后，眼睛是否还愿意停留？
3. 把页面转成灰阶后，active / link / muted / code 的层级是否仍能成立？

如果这三件事成立，`stone-600` 就不只是一个颜色选择，而是站点设计系统的一个可复用判断。

## 小结：默认层要能长期呼吸

正文色的任务不是展示个性，而是让个性有地方发生。

一个站点如果每个字都像标题，最后就没有标题；如果所有灰都在后退，最后也没有正文。
`stone-600` 的价值在于它让正文稍微降一格，但没有把阅读责任丢掉。它让页面有更多留白，
也让强调层有更多空间。

这是一种很适合当前站点的设计方向：主题不靠大色块宣告自己，而是靠默认层的呼吸、边界的克制、
少量 active 状态的清晰，慢慢形成一种耐看的秩序。
