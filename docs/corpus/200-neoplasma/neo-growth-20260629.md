这句话很短，但它不是怀旧。它真正指向的可能是：当一个项目从「一次性产出」变成
「长期维护对象」时，评价标准会换轴。快速试错、炫技框架、自动化堆叠、模型辅助，
在早期能带来推进感；但到了论文这种需要反复回看、重跑、解释、答辩、投稿、修改的
长期项目里，系统最重要的性质变成另一组词：可读、可复现、可恢复、可迁移。

所谓「古法编程」，如果只理解成不用新工具，就太窄了。它更像一种维护伦理：

**长期项目的代码和材料，首先要向未来的自己交代清楚。**

电脑能跑只是第一层。半年后的自己能不能看懂，导师质疑时能不能复盘，数据路径变了
能不能重接，模型输出不可信时能不能退回人工判断，这些才是长期项目真正的接口。

## maintainability：代码首先写给未来维护者

第一轮搜索从 `long term software maintenance Unix philosophy maintainability` 开始。
《The Art of Unix Programming》里关于 maintainability 的说法很直接：软件的可维护性，
在于不是作者的人也能理解并修改它；代码不仅要和计算机通信，也要和未来阅读、维护源码的
人通信。它还提到一个老 Unix 世界的问题：这段代码是 live、dormant，还是 dead？
如果维护痛苦超过效用，代码就容易休眠；如果休眠太久，重写反而更划算。

这给「古法」一个不浪漫的定义：古法不是旧技术，而是把维护者当作第一读者。
在论文项目里，这个维护者常常就是未来的自己。现在的自己知道 `fig_final_v7.py` 为什么
这么写，知道某个 CSV 是哪次重跑出来的，知道某个异常湖泊为什么被排除；三个月后，
这些隐性上下文会蒸发。古法编程要抵抗的不是技术新旧，而是上下文蒸发。

所以它会偏好一些看起来笨拙但可靠的实践：

- 文件名能说明来源和阶段，而不是只靠脑内记忆。
- 脚本从输入到输出有明确路径，不把关键状态藏在交互式环境里。
- 中间结果可以重新生成，不能生成时也要标注出处。
- 复杂算法旁边有解释，不把聪明留给运行时，把困惑留给人。
- 自动化可以用，但自动化产生了什么、为什么产生，要能被追踪。

这里的关键词不是「慢」，而是「低遗忘率」。长期项目最大的敌人之一，是作者本人逐渐
变成外部维护者。古法编程承认这一点，并提前给那个外部化的自己留路标。

## Lehman 定律：被使用的系统一定会继续变化

第二轮搜索转向 `Lehman's Laws continuing change increasing complexity long-lived systems`。
Lehman 的软件演化定律里，最适合借来的有两条：第一，反映现实世界的 E-type software
如果被使用，就必须持续适应，否则会越来越不能满足使用者；第二，系统不断演化时，
复杂度会增加，除非投入明确工作去降低复杂度。

这几乎可以直接挪到论文项目。论文不是写完一个脚本、生成一张图就结束。
它会被导师意见、审稿意见、数据修正、方法敏感性、图表审美、叙事重构持续拉动。
每一次「再试一个窗口」「换一种断点检测」「补一张区域图」「把 PDO / bloom 降级成
future directions」，都是继续变化。变化本身不是坏事；真正危险的是变化只增加功能，
不偿还结构。

于是论文项目也会出现软件演化里的熵增：

- 新增一个分析脚本，但没有删除旧脚本。
- 复制一份 notebooks，但两份都还能跑出不同版本的图。
- 加入一个中间数据表，但命名没有说明它属于哪次方法选择。
- 为了应付一次质疑临时补图，补图后来混进主叙事。
- 模型辅助生成解释，但解释没有被绑定到可复核的 evidence。

这些东西不一定马上造成错误。它们更像结构里的水汽，短期看不见，长期会霉。
古法编程在这里不是反对变化，而是要求每一次变化都带一点 anti-regressive effort：
重命名、删旧、写注释、记录参数、固定入口、把临时判断移出主线或转为明确分支。

如果用一句话压缩：

> 长期项目不是靠一口气推进，而是靠每次推进后仍然能被下一次推进接住。

## worse is better：能活下来的朴素，胜过无法迁移的完美

第三轮搜索查 `worse is better minimal implementation piecemeal growth software`。
Richard Gabriel 的 worse is better 常被误读成「烂也可以」。原文更细：一个 minimal
creation 可以先活下来，再按需要生长；它和 piecemeal growth 有关。这个概念危险，
因为它很容易被拿来合理化粗糙。但放在长期项目里，它也有一个清醒版本：

**先做一个能被理解、能被替换、能被继续维护的朴素系统，通常比一开始追求完整架构更稳。**

论文分析尤其如此。早期最诱人的错误，是把项目当成产品工程：搭漂亮 pipeline，写通用框架，
设计复杂配置层，试图一次性覆盖未来所有分析。但研究问题还在变，图表还在变，导师的关注点
也会变。太早冻结架构，可能会把探索期的假设硬编码成系统骨架。

这里的「worse」不是质量低，而是故意保持某种未完成：

- 先用清晰脚本而不是抽象框架，等重复模式真的出现再抽象。
- 先用 plain CSV / Parquet / Markdown 记录关键中间物，不急着塞进复杂数据库。
- 先把图的 claim 写清楚，再决定是否统一封装绘图函数。
- 先把方法分支显式放出来，而不是假装只有一条优雅主线。

这其实和最近几轮 Growth 里反复出现的实验逻辑相通：nominal treatment 和 realized
treatment 要区分，intended plan 和 delivered project 也要区分。古法编程允许 delivered
project 暂时朴素，只要它的维护史清楚，下一步可以接。

## local-first 与 plaintext：长期项目需要可迁移的底座

第四轮搜索从 `local-first software plain text longevity durable software` 进入。
Ink & Switch 的 local-first 文章把「旧式软件」的优点讲得很清楚：数据在本地文件里，
用户拥有完整 agency，可以归档、备份、用其他程序处理，不依赖某个远程服务继续存在。
Plaintext Commons manifesto 又把这个判断推到知识系统：知识应该比软件活得久；
文件夹是平台，文件是协议；工具可以来去，语料本身不该被工具占有。

这和 froQ 的知识库结构几乎同构。Corpus 用 Markdown、frontmatter、Git、目录层级和
轻量标签，把知识放在工具之下，而不是工具之内。论文项目如果也采取类似原则，
「古法编程」就会从写代码扩展成一套材料治理：

- 数据优先存在为可搬走的文件，而不是只存在于某个 app / notebook session。
- 分析入口可以通过 CLI 或脚本重跑，而不是只能在某个图形界面里手动点。
- 参数、版本、判断写在文本里，让 Git 能看见差异。
- AI 可以参与解释、改写、检查，但不成为唯一保存判断的容器。
- 生成物和来源之间有相对稳定的链接，不靠聊天上下文记忆。

这不是拒绝数据库、拒绝云、拒绝 AI。更精确地说：长期项目的 source of truth 要放在
足够朴素、可迁移、可审计的底座上。高级工具可以是加速层、索引层、协作层，不能悄悄
变成唯一地基。

## 古法编程不是反现代，而是给现代工具加地线

现在可以把「古法编程」从一种情绪词拧成一个模型。它至少有五条结构原则：

1. **可读性优先于聪明性**：未来维护者能看懂，比现在少写十行更重要。
2. **文件优先于平台**：长期材料应能离开当前工具继续存在。
3. **显式状态优先于脑内状态**：参数、版本、异常、分支判断要落到文本或日志里。
4. **渐进抽象优先于预制架构**：等重复和稳定边界出现后再抽象。
5. **恢复入口优先于一次性完美**：中断后能接回来，比某次运行特别漂亮更重要。

这些原则并不排斥新工具。相反，它们能让新工具更安全。AI 可以生成脚本，前提是脚本要
落回可读文件；自动化可以跑分析，前提是输入输出和参数可追踪；复杂 pipeline 可以出现，
前提是它从真实重复里长出来，而不是从架构欲里先验降临。

所以「古法」真正反对的不是现代性，而是无地线的现代性：工具越强，越容易把中间判断
卷进黑箱；速度越快，越容易让结构债务滞后显影。古法像一根接地线，把快速生成的电流
导回可读、可删、可复盘的材料世界。

## 给论文项目的一组轻量检查

如果把这次枝条落到论文，可以形成一个很小的检查表。它不需要变成复杂制度，
只要在每次重跑、改图、换方法后问几句：

- **入口**：如果明天重启电脑，从哪个命令或脚本继续？
- **材料**：这张图的输入数据是哪一个文件，能否追到原始数据或上游生成脚本？
- **参数**：窗口、阈值、过滤条件、随机种子、版本是否写在文件里？
- **分支**：废弃路线是删掉了、归档了，还是仍然和主线混在一起？
- **叙事**：这次分析支持的 claim 是什么，是否只是一张「好像有用」的图？
- **恢复**：如果导师三周后问「为什么不用另一个方法」，能否迅速重建当时的判断？

这里有一个判断值得留下：

> 长期研究项目的优雅，不是看起来像工程系统，而是每一个判断都能在必要时重新站起来。

论文不是纯软件，但论文越来越像一个复合系统：数据、脚本、图、叙事、文献、导师反馈、
审稿风险、AI 协助，全都缠在一起。古法编程的价值，是把这个复合系统重新拉回可维护的
地面。它不承诺一路顺滑，只承诺当系统变复杂、变旧、被质疑、被搁置又被捡起时，
还有足够多的路标能把人带回来。

这也让「长期项目应该回归古法编程」不像一句保守宣言，而像一句很硬的工程判断：
越是要走得远，越不能把未来维护者锁在现在的灵感里。
