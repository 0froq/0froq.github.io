## 今夜的入口

这次没有旧的 Growth Patrol 可以接续，000-autopsia 里还没有 `aut-growth-*` 的回声。于是我先听最近两天的改动。工作区里有一些 dashboard 文件的移动或删改痕迹，但它们更像规划系统的地壳运动，不适合在自动巡夜里贸然解释；真正亮起的是 `docs/corpus/300-putredo/put-20260606.md` 里那句很短的话：

> 下一个大概是做一个低饱和人文主义的东西。现在这个是鲜艳干净风格。

这句话值得继续长一点，因为它不是单纯的「换个配色」。它牵住了几条旧线：从 Obsidian 主题 Qlean，到 Neovim 与 VSCode 的 oQ / LiG，再到 `neo-a-syntax-lightlight-design.md` 里对语法高亮语义层级的犹疑。主题在这里不是皮肤，而是一套关于注意力分配的制度：什么应该先被看见，什么应该退到背景，什么颜色承载语义，什么颜色只承担空气。

「低饱和人文主义」这个词组尤其有意思。低饱和容易滑向温吞，人文主义容易滑向装饰性的暖色滤镜；但如果把它放进编辑器主题和知识工作环境里，它也可以成为一种很严格的设计约束：颜色不再以刺激感证明存在，而是以长期阅读、长期编码、长期写作时的耐受性证明存在。

## 我沿着它查了一会儿

我沿着「humanist」「low saturation」「syntax highlighting」「semantic tokens」查了一会儿。外部资料给了几个很有用的支点，但没有直接给出答案。

第一个支点来自设计系统对颜色的处理方式。Atlassian 的颜色系统把颜色拆成 role、emphasis、state：颜色先有职责，再有深浅，再有交互状态。这个思路和「低饱和」并不冲突，反而能避免低饱和主题最常见的问题：所有东西都柔和，最后所有东西都同等重要。低饱和不是平均降噪，而是给每种语义安排合适的音量。

第二个支点来自 Apple Human Interface Guidelines 对颜色的态度：颜色应当克制地用于沟通、连续性、状态反馈与重要信息，不应成为界面里到处闪烁的装饰。这里的关键词不是「好看」，而是 communication。若把它翻译到编辑器主题里，语法色彩的任务不是让一段代码像圣诞树，而是帮助眼睛判断结构、作用、引用、状态、危险。

第三个支点来自 VS Code 的语义高亮文档。VS Code 明确区分 TextMate grammar 和 semantic token：前者偏词法，后者依赖语言服务理解项目上下文。也就是说，`neo-a-syntax-lightlight-design.md` 里那种「function / call / struc / ref」的困惑，不只是个人命名问题，它碰到了语法高亮系统的真实边界：TextMate 很难知道一个变量在语义上是结构支点还是普通引用，Tree-sitter 和各语言 parser 也会给出彼此不一致的颗粒度。

这反而让「人文主义」这个词变得不那么虚。人文主义主题不必假装机器能完全理解代码的意义。它可以承认工具链的有限性，然后在有限的 token 分类上建立一套可解释、可迁移、可放弃的审美秩序：有些色彩用于行为，有些用于结构，有些用于材料，有些用于元信息；无法稳定识别的部分保持中性，不用颜色制造虚假的确定性。

我还看到一些现成主题对「humanist」的理解，多半走向温暖、有机、长时间使用、soft contrast。这个方向可参考，但不能直接照搬。因为 froQ 的主题线索里还有一个更硬的内核：不是只做一个温暖皮肤，而是把代码、写作、知识库、工具链放进同一个审美系统。它应该像一套小型城市照明规范：街灯温和，但路口必须清楚；建筑有阴影，但出口不能暧昧。

## 它可能继续长向哪里

### 把「低饱和」定义成注意力预算

这枝从 `put-20260606.md` 里那句「现在这个是鲜艳干净风格」长出来。鲜艳干净很适合表达完成度与明快感，但它也容易把每个 token 都推到前景。新的主题如果只是在 HSL 上降低 saturation，很可能会变成雾化版 LiG；真正值得做的是先定义注意力预算。

可以把界面分成几个层级：正文阅读层、代码结构层、即时反馈层、危险状态层。低饱和只约束常驻层，危险、选择、错误、搜索命中仍然需要足够的对比。这样「温和」不会牺牲判断速度。这个方向通向一份主题设计准则，也可能通向一个 token palette：每个颜色不是因为漂亮而存在，而是因为它负责一种认知功能。

它值得 froQ 判断，是因为这会决定下一主题的底层性格。若把低饱和看成美学风格，产物会是一个主题；若把它看成注意力经济学，产物可能是一套跨编辑器、跨知识库、跨网页的视觉协议。

### 让语法高亮承认自己的无知

这枝从 `docs/corpus/200-neoplasma/neo-a-syntax-lightlight-design.md` 长出来。那篇里最有生命力的地方不是已经分清了什么，而是坦诚地卡在「变量属于 struc 还是 ref」这类问题上。

或许可以把新主题的语法系统设计成两层：稳定语义层与猜测语义层。稳定语义层包括 keyword、string、comment、type、function definition、constant 之类跨语言相对稳定的东西；猜测语义层包括变量、调用、属性、参数等容易受 parser、LSP、语言生态影响的东西。前者给明确色相，后者给较弱的明度、字重或同色系变化。

这会通向一种很优雅的主题哲学：高亮不是宣判意义，而是标注置信度。它也能解释为什么 TextMate、semantic token、Tree-sitter 之间不必强行统一。每个系统看见的世界不同，主题要做的是提供退路，而不是把不稳定的信息涂成同样笃定的颜色。

### 从编辑器主题走向个人环境的色彩宪法

这枝从 Qlean、oQ、LiG、博客主题这些旧线长出来。主题开发一直在 froQ 的轨道里反复出现，说明它不像一次性项目，更像对「我如何安置注意力」的长期实验。

新的低饱和人文主义主题可以不只服务 VSCode 或 Neovim。它也许能被抽象成一份 `tokens.json`：base scale、accent scale、semantic roles、syntax roles、status roles、surface roles，然后再编译到 VSCode、Neovim、VitePress、博客 CSS，甚至 terminal ANSI。这样主题不再是各端分别调色，而是一套可迁移的感官基础设施。

这个方向的价值在于可持续。单个主题容易在审美疲劳后被重写；色彩宪法如果写得足够清楚，后续每一次重构都能沿着同一套约束演化。它会把「我又在重构」从消耗型循环，稍微推向滋养型迭代。

### 给「人文主义」一根可验证的骨头

这枝从词本身长出来。「人文主义」如果只落在暖色、纸感、圆角、低对比上，会很快变成风格标签。更硬的定义可能是：它尊重人的阅读疲劳、人的色觉差异、人的上下文切换成本、人的长期使用节律。

于是它需要一些可验证的骨头：正文对比至少满足 WCAG AA；非正文信息不只依赖颜色，也依赖形状、字重或位置；暗色与亮色不是简单反相，而是在不同背景亮度下保持同样的语义距离；注释不该淡到像不存在，因为注释常常是代码里最像人声的部分。

这条路通向一篇理论短文，也可能通向主题 README 的核心段落。它值得判断，是因为它能让「人文主义」从感受词变成设计原则：不是给机器界面贴上人的皮肤，而是承认使用者有眼睛、有疲劳、有偏好，也有持续工作的尊严。
