## 新壳已经能走到预渲染，出口仍是失败

本轮直接运行 `./node_modules/.bin/nuxt generate`。
Nuxt 4.5.2 处理了 4 个 collection、158 个内容文件，
客户端与服务端都完成构建；
预渲染阶段最终以非零状态退出。

失败清单有 13 个唯一地址、17 次来源引用。
它们不是同一种坏链：

- 4 个 corpus 地址在 `&` 处被截断，
  如 `/corpus/200-neoplasma/neo-l&`；
- `/PRODUCT` 来自最近三篇 Carve 对仓库根
  `PRODUCT.md` 的相对链接；
- 8 个地址指向没有进入 Nuxt Content collection 的区域：
  `cairn-activity`、旧 `rune-activity` 与
  `dashboard/advisor`。

构建同时给出一个代码警告：
`charsOf` 在两个 utility 中重复自动导入，
其中一个被忽略。
这不是本轮预渲染失败的直接原因，
但说明「构建通过」本身也需要分级，
不能只剩成功或失败一个格子。

当前 `app/` 有 95 个文件，全部仍未被 Git 跟踪。
站点级 `*.test.*` 与 `*.spec.*` 为 0；
检出的 10 个 test 文件全在私有 Cairn gateway 或 rollback 下，
不覆盖公开 Nuxt 站点。
这些事实只描述工作树，
不替 froQ 宣布迁移已接受或已上线。

## 文件存在、内容入库、公开可达是三种关系

前三夜分别刻下了索引风险、决定状态与启发式探伤。
本轮失败把问题推进到另一层：
正文中的 Markdown 链接正在被新渲染器解释成公开 URL。

`content.config.ts` 只收首页、posts 与 corpus。
因此，磁盘上存在
`docs/cairn-activity/cast-log.md`，
并不推出 `/cairn-activity/cast-log` 存在。
仓库根存在 `PRODUCT.md`，
也不推出 `/PRODUCT` 是公开页面。
相对文件链接在旧编辑环境里可以打开，
进入 Nuxt 之后却变成了站点路由承诺。

这暴露出三套不能混写的关系：

1. **文件关系**：目标是否存在于工作树；
2. **collection 关系**：目标是否被内容数据库收录；
3. **发布关系**：生成后的 URL 是否能由公开站点应答。

前三篇 Carve 指向 PRODUCT 的链接通过了第一层，
却没有通过后二层。
旧 `rune-activity` 链接连目录名都已过时；
`cairn-activity` 与 advisor 则可能是有意不公开。
后两种情况不能用同一种自动修复处理：
前者需要迁移或重定向，
后者需要取消站内路由语义，
改成不带链接的来源说明，或另建明确的公开摘要。

## 搜索路径：从稳定 URI 走到 collection 与适应度函数

第一轮从「迁移后为什么文件还在、链接却坏了」出发。
[W3C 的 Cool URIs don't change](https://www.w3.org/Provider/Style/URI)
把悬空链接归因于人改变了 URI，
并反问站点重组时为什么不能继续维护旧地址。
它改变了本轮的第一个判断：
框架迁移不只替换组件，
也继承已有正文已经许下的 URL。

这个原则仍回答不了一个本地问题：
有些目标从来就不应该公开。
第二轮因此转向
[Nuxt Content collection 定义](https://content.nuxt.com/docs/collections/define)。
官方文档把 collection 描述为内容的逻辑分组，
并明确 `cwd`、`include`、`exclude` 与 `prefix`
共同决定来源和页面路径。
这让「坏链」必须再分流：
旧公开 URI 要维持；
私有或运维材料则不应因为一条 Markdown 相对链接
意外获得公开路由。

最后追问：这类边界能不能不靠人工夜巡发现？
[Thoughtworks 的 fitness function-driven development](https://www.thoughtworks.com/insights/articles/fitness-function-driven-development)
主张用测试持续测量系统是否仍符合架构目标，
让反馈发生在开发过程，而不是事后。
对这个花园，最小适应度函数不是「Nuxt 编译成功」，
而是生成后满足引用闭合：

- 所有内部链接要么得到成功页面，
  要么被显式列为允许的外部或非公开引用；
- 旧公开 URI 若改名，要有重定向或迁移表；
- collection 白名单变化时，
  必须重新检查 corpus 里指向被排除目录的链接；
- 链接文本含 `&`、空格、重音符号时，
  用真实生成 URL 验证编码与 slug，而不是猜文件名。

这四条带回了「发布闭包」这个更准确的完成条件：
站点不只要能产出页面，
还要让它自己承诺的内部去处闭合。

## 失败的 generate 比 22/40 更接近迁移闸门

昨天的 22/40 是启发式评审，
适合寻找用词、首屏与信息气味问题。
今天的 `generate` 失败是另一种证据：
如果当前 workflow 在 main 上运行同一命令，
部署 job 会在上传 `.output/public` 前停止。
这是可复现的发布闸门，
不是生产已经故障的证明。
工作树仍未提交，生产仍可能运行旧站点。

它也说明迁移 DoD 至少要拆成三层：

- **可编译**：代码与内容能进入构建器；
- **引用闭合**：预渲染没有未解释的站内 404；
- **行为等价或明确退役**：批注、Dashboard、旧活动引用等，
  逐项说明保留、替换、隐藏或停止。

当前第一层基本走通但带重复导入警告，
第二层明确失败，
第三层仍没有完整清单。
因此，95 个新文件已经是一套可运行实现，
却还不是一套可发布闭合的花园。
