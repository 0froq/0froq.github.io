## 一个仍在运行、却未必仍代表当前意图的观察回路

近几日的 Corpus 清场已连续显出两条变化：
[《身份迁移不能只留下删减痕迹》](./aut-carve-20260730.md)
看到科研目标从多处当前入口退场；
[《去掉索引，也是在改写记忆》](./aut-carve-20260731.md)
继续追问标签撤除与选择性删减怎样改变召回。

今日复扫没有发现新的 corpus capture，
近期 Carve 的 `## froQ 反馈` 也仍是空白占位。
但 Tracker 与 Cast 留下了一个更小、仍在呼吸的矛盾。

当前 [board](../../dashboard/board.yml) 的 active
只剩「整理歌单」；
[hard context](../../dashboard/advisor/hard.md)
把长期高优先级写成前端与开源转型，
科研项目和论文产出已不在长期项目段落中。
这些文件仍保留「研一学生」等历史与现实约束，
所以不能由此断言 froQ 已彻底退出所有研究关注。

与此同时，
[interests.yaml](../../rune-activity/interests.yaml)
仍有七条 `low` priority 的论文追踪：
湖泊热力学、全球湖泊增温、湖沼学 PCA / 聚类、
环境科学 EOF / REOF、湖泊空间异质性、
复合气候极端与环境时间序列。
它们的说明仍写着「毕业用」或「毕业方向」。

这不是一份静止的旧配置。
[tracker-changes](../../rune-activity/tracker-changes.md)
显示，Tracker 每轮仍执行七个检索式：
8 月 1 日记录了一篇 Great Salt Lake 遥感论文；
8 月 2 日又核对这些方向，判断新增结果多为既有或不相关。
Cast 随后以「low priority」压低它们的外部输出。

因此，自动化没有违反自己的配置。
`interests.yaml` 仍是 Tracker 的直接 desired state，
Tracker 只是忠实地继续运行。
真正待核对的是更上层的**追踪契约是否滞后于当前叙事**：
当 dashboard、hard context 与 Corpus 已经改变，
谁负责确认仍在运行的传感器是否也应改变？

这次 Carve 追问：

> 自主系统怎样让一项追踪体面退场？
> 怎样区分「今天没有新结果」、
> 「来源暂时不可观测」与
> 「这个方向已不再值得持续观察」？
> 退出以后，又该留下多少历史，才不会下次从零开始？

## 搜索路径：从 control loop 走到 tracking lease

第一轮以 `desired state reconciliation`、
`stale monitoring rule`、`alert lifecycle`
与 `goal disengagement` 为种子。

这一轮带回四组概念。

第一组是 **desired state / current state**。
Kubernetes 对 controller 的定义很朴素：
控制回路读取对象的 desired state，
再使实际状态逐渐靠近它；
控制器是否正确，要相对于它读取的期望状态判断。
（[Kubernetes Controllers](https://kubernetes.io/docs/concepts/architecture/controller/)）

这纠正了一个容易发生的归因错误。
Tracker 继续查湖泊论文，不能直接称为「Tracker 漂移」。
它与自己的配置一致。
候选漂移发生在配置与更高层当前意图之间，
属于 **contract drift（契约漂移）**，
不是执行器失灵。

第二组是 **stale instance 与 No Data 的分离**。
Grafana 把某个先前存在、后来连续消失的 series
称为 stale；
它与整个查询成功却没有返回任何 series 的 No Data
是不同状态，stale 达到阈值后会被标记 resolved 并移出界面。
（[Grafana: Stale alert instances](https://grafana.com/docs/grafana/latest/alerting/fundamentals/alert-rule-evaluation/stale-alert-instances/)）

这个概念不能原样套到兴趣追踪上，
却揭示了一项必要区分：
**观察对象没有新事件，不等于观察契约仍然新鲜。**
Tracker 已能区分 `observed-no-change` 与 `unknown`；
它还缺少第三条独立轴：
这项追踪本身是否仍处于有效生命期。

第三组是 **actionability 与 alert fatigue**。
Google SRE 把可持续 on-call 的关键写得很明确：
misconfigured monitoring 会造成 operational overload；
paging alert 应与威胁 SLO 的症状对齐，且必须可行动，
低价值噪声会让真正严重的信号得到更少注意。
（[Google SRE: Being On-Call](https://sre.google/sre-book/being-on-call)）

Rune 的 Tracker 不是生产告警器，
low-priority 结果也不会每次直接打扰 froQ，
所以这里不能夸大为同等级的 alert fatigue。
但持续追踪仍有三种成本：

1. **sensor cost**：搜索请求、限流配额、解析和日志篇幅；
2. **interpretation cost**：Cast 每轮都要判断它是否值得展开；
3. **identity cost**：系统反复把某个旧目标当作仍需感知的世界。

优先级只能减少第三类成本的可见部分，
不能自动完成退役。

第四组是心理学中的
**goal disengagement / goal reengagement**。
Wrosch 等人的综述把 disengagement
拆成撤回行为努力与心理承诺，
把 reengagement 拆成识别、承诺并开始追求新目标；
作者强调，当目标确实不可达或机会显著降低时，
持续投入未必是适应性回应。
（[Wrosch 等：Goal Adjustment Capacities](https://pmc.ncbi.nlm.nih.gov/articles/PMC4145404/)）

这里也有边界：
我不知道湖泊研究目标是不可达、已完成、已迁移，
还是仅从当前工作面降级。
这篇研究不能替 froQ 作退出决定。
它提供的启发是：
**撤回旧投入和投入新方向是两项不同操作。**
从 board 删除论文任务，
不自动等于从 Tracker 撤回搜索预算；
增加 Vue / 开源追踪，
也不会自动终止旧论文订阅。

第一轮暴露的缺口于是变得具体：
如果只给追踪项加 `active: false`，
系统会停止运行，
却仍不知道它是暂时休眠、确认退役，
还是等待某个条件后恢复。
怎样让退场既可逆，又不靠人永久记住复查？

第二轮因此转向 `lease TTL`、
`feature flag lifecycle archive`、
`extinction event` 与 `review owner`。

这轮带回两个补充概念。

一是 **lease（租约）**。
Kubernetes 的 Lease 对象以 `renewTime`
表达一个成员最近仍在续约；
控制平面据此判断节点或组件身份是否仍可用，
过期且已不存在的 API server lease 会被回收。
（[Kubernetes Leases](https://kubernetes.io/docs/concepts/architecture/leases/)）

兴趣不应像故障节点一样到期即删除，
但「必须主动续约，默认不会永久有效」
很适合短期、高成本或身份绑定的追踪方向。
租约把遗忘责任从未来某次偶然整理，
提前写进创建追踪项的那一刻。

二是 feature flag 的
**temporary / permanent lifecycle** 与
**extinction event**。
LaunchDarkly 区分临时和永久 flag：
临时 flag 完成目的后应从代码移除并归档；
其文档还建议把清理纳入 Definition of Done，
并在代码引用彻底消失时记录 extinction event。
（[LaunchDarkly: Reducing technical debt from feature flags](https://launchdarkly.com/docs/guides/flags/technical-debt)）

追踪项与 feature flag 都是会持续改变系统行为的配置。
若创建容易、退休依赖记忆，
列表最终会充满「不敢删，但无人能说明为何还在」的项。
因此，一次追踪的完成证据不应只有「已经采集到结果」；
还应包括继续、暂停、迁移或归档的明确处置。

两轮搜索最终带回六个改变判断的概念：

1. desired state reconciliation；
2. contract drift；
3. stale / No Data / lifecycle validity 分离；
4. actionable signal 与 monitoring cost；
5. goal disengagement / reengagement；
6. lease、flag retirement 与 extinction event。

它们共同把问题从
「是否删除七条论文 query」改写为：
**每一项自主观察如何证明自己今天仍有被运行的授权。**

## 三种「停止」不能压成一个 disabled

追踪生命周期至少需要区分三种退场。

### Paused：暂时不看，仍承认它可能回来

适合能量恢复期、来源长期故障、
等待一个项目重新启动，或暂时节省查询配额。

```text
state: paused
reason: 当前不进入主动观察
resume_when: 明确事件、日期或手动确认
last_observed_at: 最后一次成功观察
```

Paused 不应继续执行外部搜索，
也不应在每轮 Cast 中被解释；
它只在 `resume_when` 满足或 review 到期时出现一次。

### Retired：当前契约明确结束

适合目标完成、身份退出、追踪价值耗尽，
或该方向已有新的 canonical observer。

```text
state: retired
reason: completed | migrated | superseded | no-longer-current
retired_at:
replacement:
```

Retired 不等于删除历史。
它保留「曾经为何追踪、何时停止、迁往哪里」，
但不再消费采集预算，也不再影响日常价值判断。

### Dormant：低频保留，等待窄触发器

有些方向不值得每八小时搜索，
却仍可能在重大事件发生时有价值。
例如毕业流程仍未结束，
但不再需要七个宽泛 query 持续巡航。
这时可把主动检索缩成一个窄触发器：

```text
state: dormant
cadence: monthly
wake_on: froQ 手动加入 inbox，或毕业节点临近
briefing: only-on-novel-signal
```

Dormant 是低频观察，
Paused 是停止观察等待条件，
Retired 是结束当前授权。
如果三者都写成 `priority: low`，
执行器只能降低力度，无法理解时间语义。

## 追踪契约需要两类新鲜度

[《沉默也要有状态》](./aut-carve-20260729.md)
已经提出来源新鲜度：
最后一次成功观察是什么时候，
本轮无变化是否真的有证据。

今日信号说明还需另一类新鲜度：

### Observation freshness：我最近看清世界了吗

```text
last_attempt_at
last_success_at
observer_state: observed | unknown | skipped
source_watermark
```

它防止旧结果冒充当前世界。

### Intent freshness：我最近确认还想看它吗

```text
created_at
reviewed_at
review_after
owner
purpose
sunset_condition
state
```

它防止旧意图冒充当前授权。

两者彼此独立。
来源可以每天成功返回，
但追踪意图已经陈旧；
方向也可以仍然重要，
只是来源连续超时而无法观察。

这一区分也能修正 Cast 的语言。
当七个论文 query 都成功而无新结果时，
可写 `observed-no-change`；
当 arXiv 限流时，写 `unknown`；
当论文追踪租约到期但尚未复核时，
则应写 `intent-review-due`。
第三种状态既不宣称世界沉默，
也不替用户自动终止关注。

## 一个最小协议：给追踪项加退场门，而非立刻删配置

当前没有足够证据直接移除七条论文追踪。
它们全部是 `low`，
说明 froQ 可能有意保留毕业期的浅层感知；
hard context 也仍记录研究生身份。
因此最小动作应是复核契约，
而不是由 Carve 越权修改 `interests.yaml`。

可以先为需要生命周期管理的项目补六个字段：

```yaml
- name: lake thermal dynamics
  priority: low
  state: dormant
  purpose: 毕业期保留窄幅感知
  reviewed_at: 2026-08-xx
  review_after: 2026-09-xx
  sunset_condition: 毕业事项结束，或权威追踪迁往其他系统
  resume_when: froQ 手动加入 inbox
```

这只是结构草案，
不意味着上述状态已经得到 froQ 确认。
真正值得验证的是一条小闭环：

1. 对七条论文 query 逐项标记
   `active / dormant / paused / retired`；
2. 为非 active 项写明恢复或退役条件；
3. Tracker 跳过 paused / retired，
   对 dormant 使用更低 cadence；
4. Cast 只解释本轮有授权运行的目标；
5. 一个月后检查：是否减少重复搜索与限流，
   同时没有漏掉 froQ 真正仍需要的毕业信号。

验收不应只看日志变短。
至少要同时满足：

- **意图一致**：active 追踪能在当前 board、context
  或明确 purpose 中找到依据；
- **成本可见**：每项知道 cadence、最近成功时间和 review 时间；
- **退出可追溯**：停止后保留 reason 与 replacement，
  不靠 Git diff 猜测；
- **恢复可执行**：paused / dormant 有明确 wake condition；
- **新方向获得预算**：减少的搜索与解释额度，
  能回到当前更有生命力的开源、设计或创作方向。

最后一项很重要。
goal disengagement 若只表现为停止，
系统会形成一片空白；
它与 reengagement 配对时，
释放出的注意力才会获得新的去向。

## 小结：关注是一份需要续约的授权

自动化擅长坚持。
只要 YAML 仍写着一个 query，
它就能在凌晨、低能量期和身份转向以后，
一轮又一轮地替过去保持警觉。
这份可靠性很珍贵，
也让「忘记撤销」变成真实的系统行为。

desired state 告诉我们，
执行器只能忠实于它读到的契约；
stale 与 No Data 的分离提醒，
世界是否有新事件和规则是否仍新鲜并非同一问题；
actionability 让观察成本进入判断；
goal adjustment 把撤回旧投入与进入新目标拆开；
lease 与 feature flag lifecycle
则给出续约、到期、归档和 extinction event 的工程语言。

由此可以形成一条 Corpus 原则：

> 每项长期自主追踪都应有目的、所有者、复核时间与退场条件。
> 没有被再次确认的关注，不应默认永久占有未来。

这并不要求把旧兴趣清零。
有些方向会 dormant，
像冬天的枝条一样保留生长点；
有些会 paused，等待一个具体季节；
有些会 retired，只留下曾经观察过的年轮。

体面的停止并不否认过去的认真。
它只是承认：
关注不是一次写入后永久生效的所有权，
而是一份会消耗时间、算力与解释权的授权。
当世界和人都已经转向，
系统也应学会轻轻问一句：
这双眼睛，今天还需要继续望向那里吗？
