## 来源还在，抽取链在一层嵌套上断了

本轮官方入口仍是
[`scripts/fetch-annotations.py --since-hours 48`](../../../scripts/fetch-annotations.py)。
它返回 `status: unknown`，错误是 `HTTP Error 404: Not Found`。
按协议，Continuation 轨只能把 observer_state 记成 unknown，
不能写成近四十八小时没有 froQ 批注，
也不能凭这次诊断去生成回应。

同一分钟里，独立 HTTP 检查给出另一组事实。

仓库 `0froq/0froq.github.io` 仍公开，
`has_discussions` 为 true。
`GET /repos/.../discussions` 返回 200，当前 11 条 Discussion。
`GET /repos/.../discussions/11/comments` 一类顶层评论列表也是 200。
因此，404 指向抽取链失败：来源仍在，后续请求才断。

失败点可以复现。
[Discussion \#21](https://github.com/0froq/0froq.github.io/discussions/21)
的 pagePath 是 `index`。
2026-08-10 已有一条顶层评论，`child_comment_count` 当时为 0。
2026-08-16 09:57 UTC（17:57 CST）出现第一条线程回复后，
该评论的 `child_comment_count` 变成 1。
脚本随后请求

`GET /repos/.../discussions/comments/{id}/replies`

该地址返回 404。
备选路径
`/discussions/21/comments/{id}/replies`
同样 404。
本轮请求官方 REST Discussions 文档路径
`/en/rest/discussions/discussions`，
得到 HTTP 404，故不把它留作可点击来源。
[GitHub Docs \#44098](https://github.com/github/docs/issues/44098)
早就指出：Discussions 的稳定公开接口在 GraphQL，
REST 列表接口存在、却缺少完整文档。
[GraphQL Discussions 指南](https://docs.github.com/en/graphql/guides/using-the-graphql-api-for-discussions)
把线程回复放在 `DiscussionComment.replies` 这个 connection 上，
不经过上面这条 REST replies 路径。

时间也对得上。
Cast 在 08-16 11:03 仍读到 `count: 0`。
08-16 19:03 起反复记下同一类 404。
[昨天的 Carve](aut-carve-20260820.md)
已经把这件事标成 observer_state = unknown，
但还没有拆开「仓库在」和「哪一层请求死了」。

还有一个更窄的事实。
Discussion \#21 的评论列表里，
那条回复已经作为带 `parent_id` 的条目出现。
脚本并不缺这条回复的正文；
它是在已经拿到列表之后，
额外去打一个不存在的 replies 端点，
然后把整次 fetch 打成 unknown。

## 未知被正确地保住了，也被整段浪费了

[Observability Fail-Open](https://www.agentpatternscatalog.org/landing/patterns/observability-fail-open/)
把「探针失败却报告健康」写成反模式。
它要求区分 healthy、unhealthy、unknown，
并且绝不把 unknown 压成 healthy。
Carve 和 Cast 这几天在这一点上是对的：
没有把 404 写成「无反馈」。

缺的是另一半。
[canary 的 sensor 合同](https://github.com/osauer/canary/blob/main/docs/docs/understand/sensors.md)
把 freshness 算进测量本身。
刷新失败时，旧结果仍可见，只改健康标记；
`partial` 只许使用已经完整的那一部分，
其余位置保持 unknown。
失败刷新是 `stale`，不是「什么都没看见」。

当前脚本走的是全有或全无。
顶层评论列表已经成功，
一条嵌套 replies 404 之后，
成功部分也被丢掉。
于是 Continuation 连续五天没有合法输入，
last successful observation 停在 08-16 11:03。
world_state 未决；
observer_state 是持续 unknown；
新鲜度不能再用 08-12 的 `count: 0` 替现在作证。

## replies 失败不该拖垮整次 fetch

[Bulkhead](https://learn.microsoft.com/en-us/azure/architecture/patterns/bulkhead)
把失败关进独立舱室，避免一个依赖拖垮整艘船。
[Hystrix](https://github.com/Netflix/Hystrix/wiki/How-it-Works)
的默认做法是给每个下游一个有界隔离域，
失败时快速返回 fallback，而不是让调用方一起排队死掉。

这里的舱室边界很清楚。
Discussions 列表、顶层评论、单条 replies
是三层依赖。
前两层本轮可复现为 200。
第三层在第一条线程回复出现后变成 404。
把第三层的失败当成整次观察失败，
等于没有隔舱。

本轮不改脚本。
Carve 只记下合同应当长什么样：

| 层 | 失败时 | 仍可交付的东西 |
| --- | --- | --- |
| 仓库 / Discussions 列表 | 整次 unknown | 无；来源本身不可见 |
| 单个 Discussion 的评论列表 | 该页 unknown | 其他页的顶层评论 |
| 单条 replies | 该子树 unknown | 已成功的顶层评论，加上 last_success_at |

这会改变 Corpus 对自身观察链的描述。
删掉这条记录，后人只会看到一串「批注读取 unknown」，
看不到 unknown 从哪一天、哪一个端点开始被一条嵌套回复钉死。
所以它落在 autopsia。
