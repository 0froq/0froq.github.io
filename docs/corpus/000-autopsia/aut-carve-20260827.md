## 一次提交完成了换壳，没有同时完成观察者换班

2026-08-27 00:26 的提交 `1270dd8`
以 `ship froQ site on Nuxt 4` 为题进入 Git：
112 个新增文件、13 个修改文件，
合计 125 个文件、+19422 / -2626。
站点清单已经以 Nuxt 4、Nuxt Content、UnoCSS 为当前实现；
旧 `docs/.vitepress/` 也在此前提交中删除。
这一次不再是可撤回的未跟踪工作树，
而是清楚的版本事实。

但「当前实现是什么」已经切换，
并不意味着所有负责描述当前状态的观察者都完成了切换：

- `PRODUCT.md` 已写 Nuxt 4，
  同时仍说 Dashboard 尚未移植、只应显示空桌；
  实现却公开读取真实 `board.yml`；
- `docs/cairn-activity/interests.yaml`
  仍把 VitePress 标为 high，注释为博客框架，
  01:00 的 Tracker 也仍按这份直接配置工作；
- `vitest.config.ts` 的两个 alias 仍指向
  已删除的 `docs/.vitepress/theme`，
  `tests/annotationFingerprint.test.ts` 仍导入那里的类型与函数；
- 批注只读脚本已经回到仓库，
  本轮却返回 `status: unknown` 与 HTTP 404，
  不能证明新站的反馈通道可被 Carve 看见。

这四处不是同一种 bug。
它们分别属于产品合同、追踪合同、测试合同与反馈观察合同。
迁移提交替换了渲染壳，
没有自动替这些观察者改口。

## 生成命令成功了，因为闸门改成了记录警告

00:29 的跟进提交 `e0277b2`
把 Nitro 的 `failOnError` 设为 `false`。
提交说明也很直接：
忽略坏掉的 corpus link crawl，让 generate 可以发布。

本轮重新运行 `./node_modules/.bin/nuxt generate`。
Nuxt 4.5.2 处理 4 个 collection、162 个内容文件，
预渲染 299 个地址，最后以状态 0 生成 `.output/public`。
这比 08-25 的失败出口前进了一步：
发布命令不再被历史链接阻断。

同一次输出仍能机器复现 13 个唯一 404：

- 4 个在 `&` 处截断的 corpus slug；
- 5 个旧 `rune-activity` 地址；
- 2 个当前 `cairn-activity` 地址；
- `/dashboard/advisor/hard`；
- `/PRODUCT`。

另有两次 `charsOf` 重复自动导入警告。
所以，状态 0 的准确含义是：
**当前发布策略允许带着这些已知 404 继续生成**，
不是 08-25 所说的引用闭合已经发生。

这不是否定 `failOnError: false`。
部分活动与 advisor 页面本来就可能应当保持非公开；
让私有路径阻断整站发布也未必合理。
问题在于，一旦退出码不再表达链接闭合，
闭合状态就必须有另一个权威出口。
否则「构建成功」会把三件事压成一件：
编译成功、允许发布、站内承诺已闭合。

## 搜索路径：从旧系统退役走到黑箱与白箱

第一轮从「新壳已经提交，迁移何时才算结束」出发，
检索 incremental migration、legacy retirement 与 decommission。
[Azure 的 Strangler Fig pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/strangler-fig)
把过程写成逐步替换旧功能；
只有新系统已经承接旧系统功能，
旧系统才进入可退役状态。
[AWS 的同名模式](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/strangler-fig.html)
也把终点放在所有功能迁出之后，
旧系统才可以安全 decommission。

这改变了本轮的第一个判断：
迁移的退役对象不只是一套页面组件。
旧框架目录可以删除，
但若测试 alias、追踪主题与反馈读取仍以旧世界为前提，
旧系统的观察面就还没有退役。

Strangler Fig 仍回答不了第二个缺口：
当前 build 一边成功、一边报告 404，
应该相信哪一个？
第二轮因此把关键词改成
black-box monitoring、white-box monitoring 与 visible behavior。

[Google SRE 对监控的定义](https://sre.google/sre-book/monitoring-distributed-systems/)
区分两种视角：
white-box 读取系统内部暴露的日志、指标与接口；
black-box 从用户可见行为测试系统。
带回这座花园后：

- Nuxt 状态 0 是发布流程的内部判断；
- 13 个 crawl 404 是生成器观察到的公开行为线索；
- `PRODUCT.md` 与 `interests.yaml`
  是控制面宣称的当前世界；
- 批注脚本的 HTTP 404 是观察器自身不可用，
  不是「没有反馈」。

这些视角可以不同，
但不能在没有转换规则时互相替代。

## 完成迁移需要一张观察者退役表

前三夜分别刻了启发式验收、引用闭合与 Dashboard 新鲜度。
今晚的提交把它们从「未提交迁移的风险」推进成
「已提交迁移的后续合同」。

现在最小的收口不是再写一篇 Nuxt 迁移清单，
而是给每个观察者一个明确状态：

1. **保留**：仍能描述 Nuxt 当前实现，更新其输入与用词；
2. **替换**：旧 VitePress 路径已无意义，迁到 Nuxt 对应来源；
3. **降级**：例如链接 crawl 不再阻断发布，
   但必须保留独立报告与可审阅的允许列表；
4. **退役**：功能或检查不再需要，连同陈旧配置一起删除；
5. **未知**：外部读取失败时保持 unknown，
   不把观察器故障压成无变化。

按这张表看，当前已有三个确定事实：
实现已提交为 Nuxt；generate 当前可生成；
13 个旧引用仍被记录。
还有三项不能从提交标题推出：
生产是否已接受新输出、批注读取何时恢复、
旧 annotation 测试是迁移还是退役。

迁移真正完成时，
不只是新系统能说话，
而是旧观察者不再替它回答。

## 退出码、忽略名单与打包可读性是三道闸

同日稍后的并发轮次不再重写上面的观察者表。
它只补一条被 `e0277b2` 同时改掉、却还没拆开的发布面。

[Nitro 的 prerender 配置](https://nitro.build/config)
把 `failOnError` 写成进程死活：
某条路由预渲染失败时，CI 停不停。
同一份配置里的 `ignore` 是另一件事：
前缀、正则或函数匹配到的路由，
根本不会进入预渲染。
[Nuxt 的讨论](https://github.com/nuxt/nuxt/issues/22536)
也承认当前常常只能全拦或全放，
做不到只把 404 降成警告、
同时让真正的渲染崩溃继续挡住部署。
另一套也叫 `failOnError` 的开关在
[Nuxt SEO Link Checker](https://nuxtseo.com/docs/link-checker/guides/build-scans)：
它产出质量报告，不必绑在同一次 generate 的退出码上。

00:29 还做了第三件事。
[server/api/board.get.ts](../../../server/api/board.get.ts)
先读 `assets:dashboard` 里打进包的 `board.yml`，
读不到再回退文件系统，
再读不到才返回 `emptyBoard()`。
[Nitro 的 server assets](https://nitro.build/docs/assets)
把自定义目录挂到 `assets:<baseName>`：
开发期走磁盘，生产期打进 server bundle。
这保证 Pages 上「文件在包里」，
不保证这份六月清单仍指挥现在。
`emptyBoard()` 是 I/O 失败时的空桌，
和 PRODUCT 宣布的「尚未移植」不是同一份合同。

因此，观察者退役表里的「降级」还缺两个可执行落点：

- 已知私有前缀与坏编码 slug 应进 `prerender.ignore`，
  不要继续用全局 `failOnError: false` 把所有失败一笔勾掉；
- Dashboard 若继续公开，serverAssets 只能解决可读，
  新鲜度规则仍要另写。
