## 内容

Vue 3.6 进入 RC（Release Candidate）阶段，意味着 API 冻结、功能完整，后续只有 bug 修复和
性能微调。这是 RC1，通常 RC 周期 2-4 周后出 stable。

froQ 的 interests 里给 Vue 标的 `priority: high`，备注是「关注 3.6 RC → stable、Vapor Mode、
与 Rolldown/Vite 集成」——这三个焦点正好对应了 3.6 的核心看点：

- **Vapor Mode（无虚拟 DOM 编译模式）**：3.6 是 Vapor Mode 从实验走向可用的关键版本。
  目前仍是 opt-in，但 RC 阶段的 API 形态基本决定了后续生态的接入方式。
- **Rolldown 集成**：Vite 8 已将 Rolldown 作为默认打包器，Vue 3.6 的 SFC 编译器需要
  适配 Rolldown 的插件机制。froQ 的 blog 跑在 VitePress（底层 Vite + Vue），这条链路
  的兼容性直接影响后续升级路径。
- **TypeScript 支持**：froQ 同时追踪 TS 7.0，而 Vue 3.6 的 TS 类型系统需要适配
  TS 7.0 的新特性（尤其是 Corsa 原生编译器带来的类型推断变化）。

当前 Tracker 数据还显示：Vite 在 8.1.5，VitePress 在 2.0.0-alpha.18，Rolldown 在 1.2.0。
这是一个典型的「底层已就位、上层等稳定」的生态阶段——底层工具链（Rolldown、Vite 8）
已经迭代到了相对成熟的版本，等待 Vue 3.6 stable 完成最后的对齐。

## 对 froQ 的影响

**短期（RC 阶段）**：

- 不需要立即行动。RC 阶段不值得在生产 blog 上升级，但可以关注 RC 的 changelog 中
  breaking changes 部分，提前评估对 VitePress 自定义主题代码的影响。
- 有一个低成本验证实验可以做：在 blog 项目的 `package.json` 里加一个
  `"vue": "3.6.0-rc.1"` 的 resolutions/overrides，跑一次 `vitepress build`，
  看是否通过。如果通过，说明兼容性风险低；如果炸了，可以在 stable 前给上游提 issue。

**中期（stable 发布后）**：

- VitePress 目前依赖 Vue 3.x，VitePress 2.0 alpha 和 Vue 3.6 stable 的搭配
  是 blog 后续升级的基准组合。等两者都 stable 后一次性升级，比分别追 alpha/RC
  更省心。
- Vapor Mode 值得单独关注——如果 VitePress 2.0 默认启用 Vapor Mode，
  blog 的构建速度和产物体积会有显著改善。

**判断**：这是一个「知道就好，不急行动」的信号。但作为 froQ 主栈的核心依赖，
RC 阶段的出现本身就值得标记——说明 Vue 3.6 已经过了功能迭代期，
方向不会大变了。
