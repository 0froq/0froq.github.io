## 核心观察：你的 tag 体系已经是一张图

蛙蛙的 flat-tag 系统中，每条笔记都有 `tags` 和 `tagsExtended` 两个字段。当前的生成逻辑（`generate-tags.mjs`）把 tags 转成静态路由和树状索引。

但从图论的角度，这个数据结构天然包含三条边类型：

| 边类型 | 定义 | 来源 |
|--------|------|------|
| **层级边** | `scope/work/coding` → `scope/work` | `/` 分隔符 |
| **共现边** | 同一篇笔记上同时出现的两个 tag | `tags` 数组 |
| **弱关联边** | tag in `tags` ↔ tag in `tagsExtended` | `tagsExtended` 字段 |

当前的 Tags 页面只利用了层级边（树展开）。共现边和弱关联边完全没有被使用——而它们恰恰是 corpus 发现价值的核心。

## 对 blog 环境的约束评估

### 环境快照
- VitePress 2.x，客户端渲染 Vue SPA（无 SSR）
- Tag 数据来自 `scripts/generate-tags.mjs` → `tags.json`
- 文章数据来自 `corpus.data.ts` + `posts.data.ts`
- 当前 tag 页面使用 `TagTreeNode` 组件做层级展开

### 关键约束
1. **纯前端** — 没有后端 API，所有计算在浏览器端
2. **静态 JSON** — tags.json 在 build 时生成，运行时不变
3. **400+ 文章** — corpus + posts 合计，tag 总数约 80+
4. **用户设备性能良好** — 蛙蛙用本地硬件，不是低端移动设备
5. **无新增依赖偏好** — 能少一个 npm 包就少一个

## 渐进式实现路径

### Phase 0：现状（已实现）

静态层级树 → 用户展开节点浏览 tag → 进入详情页查看文章列表。

当前的 Tags 页面已经做得不错：层级树 + 计数（exact / total）+ 详情页的 In This / In Extended 分离 + 鼠标悬浮动效。

### Phase 1：共现矩阵（纯数据，零 UI 改动）

**思路**：在 `corpus.data.ts` 或 posts data loader 中加一个计算逻辑，输出 `cooccurrence.json`：每个 tag 对的共同文章数。

**复杂度**：极低（~30 行数据聚合），不涉及任何组件改动。

**产出**：给未来 Phase 2/3 提供数据燃料。即使不马上用，数据到位后决策空间更大。

**为什么不现在做**：除非蛙蛙明确想往这个方向走，否则提前生成只会增加构建噪音。

### Phase 2：标签组合过滤器（新增 Vue 组件，零新增依赖）

**核心交互**：在 Tags 页面增加过滤轴——选择 `#kind/note` + `#scope/work/coding` → 只看同时满足的文章。

**实现方式**：用一个 `computed` 基于 `tags.json` 和文章数据推导出每个 tag 维度的文章集合，然后用 `v-for` + `v-if` 做交集。不需要 Vuex/Pinia，纯 `computed` 就够。

**可复用性**：这个组件可以放在 Tags 页面，也可以放在 Dashboard，甚至可以作为全局搜索的替代入口。

**取舍**：蛙蛙的 tag 没有显式的维度标注（kind/origin/source/scope 是命名约定而非元数据），所以过滤器的维度划分需要硬编码前缀匹配，或者让用户手动选择后自动推测维度。前者更可靠，后者更酷但容易误判。

### Phase 3a：共现推荐（轻量，高 UX 回报）

**核心交互**：在 tag 详情页底部显示「经常一起出现」的 tag 列表。

**示例**：看 `#scope/work/coding` 时，提示「常与此标签共现：`#kind/note` (12 次)、`#growth` (7 次)、`#scope/fmi` (5 次)」

**实现**：基于 Phase 1 的共现矩阵，取前 N 个共现 tag。纯 computed，无外部依赖。

**价值**：成本极低（一个 computed + 几行模板），但显著提升发现感。用户点进一个 tag 后，自然看到能去的「下一站」。

### Phase 3b：标签组合 Drill-Down（中量，导航重构）

**核心交互**：从「选择一个 tag → 看文章列表」变为「选择一个 tag → 看它与其他 tag 的搭配 → 缩小范围 → 看文章列表」。

**实现**：复用 Phase 2 的过滤器组件 + 新增 Drill-Down 导航。本质上是用交互流程替代静态列表。

**取舍**：这改变了 tag 页面的核心交互模式。如果蛙蛙习惯于直接看到文章列表，那么加一层中间筛选会增加操作步数。可行方案：保留当前详情页作为默认视图，把组合过滤做成侧边栏或叠加层，不干扰直接浏览。

### Phase 4：图可视化（依赖选型 + 按需集成）

**候选库**（基于 06-21 的对比）：
- **Sigma.js**：WebGL 渲染，适合 100-1000 节点，纯前端无需 Canvas 脏检查，与 Vue 集成干净（ref + mounted 注入）
- **vis-network**：API 最易上手，但包体积较大（~200KB gzip）
- **Selma**：专为语义关系设计的轻量库，API 很新，但社区较小

**推荐顺序**：先 Phase 3b（交互替代视觉），确认用户对「发现层」有需求后，再引入可视化渲染。

**可视化不解决导航问题**——06-20 笔记里的核心 insight：hairball 不是渲染问题，是数据模型问题。先确保数据模型能支撑发现，再看要不要加图。

## 整体路线图与依赖

```
Phase 0 ─────────────────────→ 当前状态
  │
  ├──> Phase 1 (共现矩阵) ──→ Phase 3a (共现推荐)
  │                               │
  └──> Phase 2 (组合过滤) ──→ Phase 3b (Drill-Down)
                                      │
                                      └──> Phase 4 (图可视化)
```

每个 Phase 是独立的，不需要等前面的完成。但做 Phase 2 之前做 Phase 1 会有数据冗余——Phase 1 的数据可以加速 Phase 2 的共现排序。

## 我的判断

这张图里最值得先做的是 **Phase 3a（共现推荐）**：

- 成本最低（~30 行 js + 几行模板）
- UX 回报最直接（用户点进 tag 页立刻看到「下一站」）
- 不改变现有交互模式（不会让已习惯旧版的蛙蛙感到突兀）
- 数据可以留作 Phase 4 的输入

第二个值得做的是 **Phase 2（组合过滤）**，但建议去调研一下用户的使用习惯——如果蛙蛙主要通过 Tags 页面浏览 corpus，那么组合过滤能大幅提升发现效率；如果蛙蛙更多通过 corpus 层级（000-autopsia / 100-ingesta / ...）浏览，那么组合过滤的价值会降低。

Phase 4（图可视化）建议等到 corpus 规模再大一轮（700-1000+ 笔记）或者出现明显的「找不到东西」抱怨时再考虑。当前 400+ 笔记规模下，层级树 + 共现推荐 + 组合过滤已经能覆盖大部分发现场景。
