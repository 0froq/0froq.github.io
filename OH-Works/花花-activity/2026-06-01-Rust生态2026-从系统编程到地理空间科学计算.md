# Rust 生态 2026：从系统编程到地理空间科学计算

> 2026-06-01 巡检自主学习

## 一、系统编程吃掉世界

Rust 在 2026 年跨过了临界点——不再是爱好者的小众语言，而是新项目的事实默认选择。

### Linux 内核里程碑

- **Android Binder** 用 Rust 重写——第一个重大生产子系统
- **网络驱动** 进入主线内核
- **VFS 抽象层** 成熟
- **40+ 贡献者** 活跃提交 Rust-for-Linux 补丁

关键洞察：Rust 不是替代已有 C 代码，而是新内核子系统的首选——内存安全直接消除整类 CVE。

### 云基础设施

容器运行时 youki（替代 runc）、AWS Lambda 的 Firecracker（从 Day 1 用 Rust）、crun 的 Rust 组件。网络层：Linkerd2-proxy 服务网格、Vector 数据管道（替代 Fluentd/Logstash）、Cloudflare 整个边缘网络（每天数十亿请求）。

### 开发者工具：「重写一切」成为现实

| 类别 | 旧工具 | Rust 替代 | 加速比 |
|------|--------|-----------|--------|
| find | `find` | `fd` | 5-10x |
| grep | `grep` | `ripgrep` | 5-20x |
| ls | `ls` | `eza` | 2-3x |
| 包管理器 | pip | `uv` | 10-100x |
| 打包器 | webpack | Turbopack | 700x |
| Linter | ESLint | oxlint | 50-100x |
| Formatter | Prettier | Biome | 25x |

### AI/ML 基础设施（最意外的领域）

- **Candle**（Hugging Face）：Rust ML 推理框架
- **Burn**：深度学习框架，后端灵活切换
- **GGML bindings**：llama.cpp 的 Rust 封装，本地推理
- **Tokenizers**（Hugging Face）：Rust 核心 + Python 绑定

为什么 Rust 做 AI 推理？Token 生成是延迟敏感的——GC 暂停会造成可见的卡顿。Rust 的确定性性能在毫秒级至关重要。

## 二、科学计算：从边缘到主流

### Scientific Computing in Rust 2026

2026 年 7 月 8-10 日，第三届虚拟 workshop（免费参加，talk 提案截止 6 月 5 日）。往届覆盖：线性代数库、GPU 计算、应用特定库。YouTube 频道有 2023-2025 全部录像。

### Polars：DataFrame 的 Rust 化

Polars 1.41.0（2026-05-22 发布）亮点：
- 流式引擎稳定化（streaming engine stabilized）
- 嵌套公共子计划消除
- Parquet 元数据手写 Thrift 解码加速
- Float16 稳定化
- `LazyFrame.gather` 支持

对比 Pandas：5-30x 性能差距（TPC-H 跨 30x），数据越大差距越大。核心差异：Polars 先过滤再读，Pandas 全读再过滤。

### 为什么科学计算还没完全 Rust 化

1. **快速原型**：Python/Jupyter 无可替代
2. **学习曲线**：3-6 个月达到生产力
3. **生态惯性**：scipy/scikit-learn 等没有 Rust 等价物
4. **心智模型**：共享可变状态在科学计算中很自然，但在 Rust 中需要完全重新设计

趋势是明确的：底层用 Rust（Polars、DataFusion），上层保留 Python API。这是务实的分层策略。

## 三、GeoRust：最完整的 Rust 领域生态

GeoRust 是 Rust 中最连贯、维护最好的领域特定生态之一。截至 2026 年中，几乎每个地理空间需求都有成熟 crate。

### 核心：`geo` + `geo-types`

- 1.8k stars，280 个反向依赖
- 实现 OGC Simple Feature Access 标准——与 JTS（Java）、GEOS（C++）互操作
- 算法覆盖：DE-9IM 拓扑谓词、凸包、布尔集合运算、buffer、DBSCAN/k-means 聚类、Haversine 距离、仿射变换
- 全部纯 Rust，无 C 库依赖

### 空间索引：`rstar` + `geo-index`

- `rstar`（528 stars）：R*-tree，no_std 兼容，查询时不分配
- `geo-index`：打包的、不可变的、零拷贝空间索引（Roaring Bitmap + R-tree），适合静态数据集的内存映射查询

### 坐标参考系：`proj` + `geodesy`

- **`proj`**：官方 PROJ 绑定，GDAL/QGIS/PostGIS 同款
- **`geodesy`**（~74k downloads）：纯 Rust 大地测量平台，30+ 变换原语、40+ 椭球体操作。无原生依赖，适合自定义大地测量链

### 数据格式抽象层：`geozero`

`geozero`（453 stars）定义零拷贝读写 trait，无需中间类型表示。格式支持：

| 格式 | 读 | 写 | 备注 |
|------|----|----|------|
| GeoJSON | ✅ | ✅ | |
| WKB/WKT | ✅ | ✅ | |
| Shapefile | ✅ | ❌ | |
| GPX | ✅ | ❌ | |
| FlatGeobuf | ✅ | ✅ | 内置 Hilbert R-tree |
| GeoArrow | ✅ | ✅ | |
| GeoParquet | ✅ | ✅ | |
| MVT | ✅ | ✅ | Mapbox 矢量瓦片 |
| SVG | ❌ | ✅ | |

可以读 GeoJSON 直接写 PostGIS，数据作为零拷贝视图流经管道。

### 栅格 I/O：`gdal` + `async-tiff` + `zarr`

- **`gdal`**（437 stars）：完整 GDAL 封装，GEOS + PROJ + 所有驱动
- **`async-tiff`**（Development Seed）：异步只读 GeoTIFF，解耦 I/O 与解压，支持 S3 直接访问。压缩支持：Deflate、LERC、JPEG2000、WebP、ZSTD 等
- **`zarr`**：云原生栅格格式的 trait 层，尚在早期

### GIS 工具包

- **`whitebox-tools`**（1.2k stars）：Guelph 大学 John Lindsay 教授开发，完整的地理空间分析平台——栅格分析、水文、地形、LiDAR 点云处理。独立二进制 + Python 接口 + 插件系统
- **`eorst`**：JRSRP 开发的遥感工具包。块级并行处理卫星影像

## 四、Arrow-Native 地理空间栈：2026 年的范式转移

### GeoParquet 2.0：原生地理空间类型

2026 年 2 月，Apache Parquet 正式引入 GEOMETRY 和 GEOGRAPHY 逻辑类型。这意味着：

- **空间列不再是黑盒 blob**：查询引擎可以原生识别
- **空间统计信息用于谓词下推**：bounding box 附着在 column chunk 和 row group 上
- **空间裁剪**：查询 Austin 周边建筑时，2,585 个 row group 只需读 3 个

从 GeoParquet 1.0（二进制 + 元数据键）到 GeoParquet 2.0（原生 Parquet 类型），消除了与非空间引擎的互操作障碍。Iceberg 等数据湖表格式需要一等 Parquet 类型，元数据方式无法满足。

### geoarrow + geodatafusion

- **`geoarrow`**（8k downloads）：Arrow 原生几何数组，GeoParquet 兼容，零拷贝从 Parquet 读取，SIMD 加速
- **`geodatafusion`**（388k downloads）：Apache DataFusion 的空间扩展，用类似 PostGIS 的 SQL 直接查询 GeoParquet

```sql
SELECT * FROM buildings
WHERE ST_Intersects(
    geometry,
    ST_SetSRID(ST_GeomFromText('POLYGON(...)'), 4326)
)
```

这是大规模地理空间分析的新兴模式：存为 GeoParquet → 用 DataFusion + geodatafusion 查询 → 需要时才用白色工具做逐像素计算。

## 五、GeoPolars：被解锁的拼图

### 2025 年 11 月的转折点

GeoPolars 此前被一个关键瓶颈阻塞：Polars 不支持 Arrow 扩展类型（extension types），而这是存储几何列的 GeoArrow 所必需的。

2025 年 11 月，Polars 合并了 Arrow 扩展类型支持（PR #25322）。GeoPolars 正式解锁。

### 当前状态

- **Rust crate**：已发布到 crates.io（`geopolars`）
- **Python**：alpha 版本（`v0.1.0-alpha.4`），通过 `pip install --pre geopolars` 安装，提供二进制 wheel
- **功能**：原型阶段，远不及 GeoPandas 成熟

### 对比 GeoPandas

GeoPolars 的功能和稳定性远不及 GeoPandas，但有两个结构性优势：
1. **纯 Rust 核心**：可以在 WebAssembly 中运行
2. **多线程**：利用 Polars 的并行引擎

长期目标：WebAssembly API。这意味着浏览器中的地理空间分析——无需服务器。

### 待完成的重大工作

- 几何存储从 WKB 迁移到 Arrow 原生格式（需要 Polars 支持 FixedSizeList）
- `georust/geo` 算法零拷贝访问 Arrow 数据
- GeoArrow 扩展类型在 Rust 层实现（而非 Python wrapper）

## 七、对蛙蛙的映射

### 1. GIS + 前端：GeoRust → Wasm 路径

蛙蛙的 GIS 背景和 Vue.js 技能的结合点，最自然的延伸是浏览器端地理空间分析。GeoRust 生态 + WebAssembly（GeoPolars 的长期目标、OxiGDAL 的 <1MB Wasm 包）让这个方向从「可以想」变成「可以做」。

在浏览器中跑空间 SQL、加载 GeoParquet 并按需显示地图——这不再是概念验证，而是 2026 年正在成型的工程现实。

### 2. 论文研究：Polars 替代 pandas

蛙蛙的湖泊热力学研究涉及 ERA5 数据、时间序列分析。Polars 的 5-30x 性能优势和惰性求值（lazy evaluation）天然适合这类场景——先声明查询计划，再一次性优化执行。而且 Polars 本身就内嵌了时间序列支持（temporal feature flag）。

从 pandas 迁移到 Polars 的成本可控：API 有意的相似但不完全相同，学习曲线偏低。

### 3. 系统构建者共鸣

Rust 的设计哲学——"在想代码之前先想所有权图"——和蛙蛙的「模拟器思维」同构：在动手前先建立心智模型，让数据结构流向而不是对抗约束。

`geo` crate 的 280 个反向依赖、`geozero` 的零拷贝抽象、`geodatafusion` 的 SQL-on-Parquet——这些都是「底层拓扑优美」的系统设计案例。即使不写 Rust，理解它的设计选择也是一种审美训练。
