## 二、OxiGDAL：GDAL 的 Rust 重生

### 为什么需要替代 GDAL？

GDAL 是 GIS 行业的基石，但它是 C/C++ 写的，带着几十年的技术债：

- Docker 镜像动辄几百 MB 甚至 GB
- 交叉编译地狱（想在浏览器跑？不可能）
- 内存安全问题
- 线程不安全的 API

### OxiGDAL 做了什么

**完全用 Rust 从零重写，不是 Rust binding**。v0.1.3（2026-03-21）已有 ~54 万行 Rust，76 个 workspace crate，15 个格式驱动。

核心对比：

|            | GDAL (C/C++)                            | OxiGDAL (Rust)            |
| ---------- | --------------------------------------- | ------------------------- |
| 依赖       | C/C++ toolchain, PROJ, GEOS, libcurl... | `cargo add oxigdal`       |
| 交叉编译   | 每个目标都痛苦                          | 原生支持 Wasm/iOS/Android |
| 内存安全   | 手动管理                                | Rust 编译期保证           |
| 并发       | 线程不安全 API                          | 无畏并发                  |
| 二进制大小 | ~50MB+ 单体                             | 按需付费                  |
| Wasm       | 不支持                                  | **< 1MB gzipped**         |
| 错误处理   | C error codes                           | Rich typed Result         |

### 性能

- **GeoParquet 读取**：比传统 GeoPandas 快 10x（Arrow-native）
- **CRS 变换**：100 万点 < 10ms
- **SIMD 加速**：AVX2/AVX-512（x86）和 NEON（ARM）自动向量化

### Wasm 的意义

`oxigdal-wasm` 包 < 1MB gzipped。这意味着你可以在浏览器里：

```javascript
import { WasmCogViewer } from '@cooljapan/oxigdal'

const viewer = new WasmCogViewer()
await viewer.open('https://example.com/cog.tif')
// 直接解析 Cloud Optimized GeoTIFF，在浏览器本地渲染瓦片
// 不需要服务器端瓦片服务
```

### 路线图

- **v0.2.0** (Q2 2026)：100+ 投影系统、GPU 扩展、ML 管线
- **v0.3.0** (Q3 2026)：Streaming v2、云原生瓦片服务 v2
- **v1.0.0** (Q4 2026)：LTS 承诺、企业合规认证

## 三、DuckDB-WASM + 空间扩展：浏览器里的 SQL 地理引擎

### 架构思路

DuckDB-WASM 让整个 DuckDB（含空间扩展）在浏览器里跑。这意味着你可以：

1. 在浏览器加载 Parquet/GeoJSON/GeoPackage 文件
2. 用完整 SQL + PostGIS 兼容函数做空间查询
3. 直接用 `ST_AsMVT` 生成 Mapbox Vector Tiles
4. 通过 MapLibre GL JS 自定义协议渲染

**整个管线不依赖任何后端服务。**

### 性能对比

DuckDB-WASM v1.30.1+ 支持 `ST_AsMVT` 和 `ST_AsMVTGeom`，直接生成 MVT：

| 方法                           | 总耗时 | 加速比   |
| ------------------------------ | ------ | -------- |
| ST_AsGeoJSON + geojson-vt 转换 | 213ms  | 1x       |
| Native ST_AsMVT                | 31ms   | **6.8x** |

### 核心 SQL 模式

```sql
WITH tile_data AS (
  SELECT {
    'geometry': ST_AsMVTGeom(
      ST_Transform(
        ST_SimplifyPreserveTopology("geom", 0.0001),
        'EPSG:4326', 'EPSG:3857', true  -- always_xy=true 关键
      ),
      ST_Extent(ST_TileEnvelope(${z}, ${x}, ${y})),
      4096,  -- MVT 标准 extent
      256,   -- buffer
      false
    ),
    'name': TRY_CAST("name" AS VARCHAR),
    'value': TRY_CAST("value" AS INTEGER)
  } AS feature
  FROM your_table
  WHERE "geom" IS NOT NULL
    AND ST_Intersects(
      ST_Transform("geom", 'EPSG:4326', 'EPSG:3857', true),
      ST_TileEnvelope(${z}, ${x}, ${y})
    )
  LIMIT 10000
)
SELECT ST_AsMVT(feature, 'v', 4096, 'geometry') AS mvt
FROM tile_data
WHERE feature.geometry IS NOT NULL;
```

### MapLibre 自定义协议集成

```typescript
maplibregl.addProtocol('duckdb', async (params) => {
  const { tableSpec, zxy } = parseDuckDBTileUrl(params.url)
  const mvt = await generateVectorTile(conn, tableSpec, zxy)
  return { data: mvt }
})

// 然后像普通瓦片源一样使用
map.addSource('my-data', {
  type: 'vector',
  tiles: ['duckdb://table/mytable/{z}/{x}/{y}'],
})
```

## 四、三件事情的汇聚

OxiGDAL、DuckDB-WASM、MapLibre/DeckGL 这三条线在 2026 年交汇，形成了一个新的范式：

### 旧范式（2023 以前）

```
GeoJSON/Shapefile → Python 预处理 → PostGIS → 瓦片服务 → 浏览器渲染
                    ↑ 需要服务器                ↑ 需要服务器
```

### 新范式（2026）

```
Parquet/COG/GeoPackage → 浏览器加载 → DuckDB-WASM 查询 → ST_AsMVT → MapLibre 渲染
                          ↑ 全部在浏览器本地完成
```

### 这意味着什么

1. **零服务器 GIS** — 数据可以直接从对象存储（S3/R2）加载到浏览器，分析和可视化全在客户端完成
2. **迭代速度飞跃** — 改 SQL 查询立刻反映到地图上，不需要重建瓦片缓存
3. **可分发性** — 一个静态 HTML 页面就是完整的 GIS 应用，不需要后端
4. **离线 GIS** — 配合 Service Worker + IndexedDB，可以实现完全离线的地理空间分析

### 对蛙蛙的意义

作为同时写 Vue.js 前端和处理气候/GIS 数据的人，这套技术栈是你两个世界的直接桥梁：

- **湖泊热力学数据可视化**：ERA5 NetCDF → DuckDB-WASM → 浏览器端统计分析 + 瓦片渲染
- **论文研究工具**：数据探索不需要在 Python 和浏览器之间来回切换，全在浏览器完成
- **开源贡献方向**：DuckDB-WASM + MapLibre 的 Vue 3 封装组件是一个生态缺口
- **OxiGDAL 潜力**：v1.0.0 今年 Q4 发布，是进入 Rust + GIS 开源贡献的绝佳窗口

### 局限与坑

- **浏览器内存上限**：超大数据集需要预处理（Parquet 分区、列裁剪、预聚合）
- **复杂几何性能**：密集多边形集群可能拖慢渲染，需要 `ST_SimplifyPreserveTopology`
- **Wasm 内存搬迁**：从 DuckDB-WASM 取 Uint8Array 时要 copy（ArrayBuffer detachment 问题）
- **多进程缺失**：浏览器端目前没有真正的多线程 GIS 处理（SharedArrayBuffer 需要 COOP/COEP headers）
