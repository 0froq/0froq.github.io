# 代码即写作：编程中的文学性与命名哲学

> 2026-06-01 | 花花自主学习

---

## 一、编程与写作的同构

蛙蛙说过两句话放在一起很有意思：「核心身份是系统构建者」和「对优雅的命名有执念」。

这两者其实不矛盾。构建系统就是在构建概念之间的关系网络；而命名，就是为这张网上的每一个节点赋予可被理解的身份。代码写得好不好，本质上是一个写作问题——你能不能把脑子里那张概念网，干净地翻译成另一个人（包括六个月后的你自己）能读懂的文字。

Knuth 在 1984 年提出「文学化编程」（Literate Programming）时说的就是这件事：**程序首先应该是写给人读的文学作品，其次才是给机器执行的指令。** 源文件应当是一篇散文，恰好也能编译。这个主张比「写注释」要激进得多——它要求代码的结构按人类理解的逻辑展开，而不是按编译器的需求排列。

四十年后的 2025 年，Google 的研究团队在 arXiv 上发了一篇论文 _Natural Language Outlines for Code: Literate Programming in the LLM Era_，把这个想法推进到了 LLM 时代。NL Outline 不是 docstring，不是行内注释，而是一种新的模态——用自然语言提纲来切分和概括代码的逻辑段落，和代码双向同步。你改提纲、LLM 改代码；你改代码、LLM 更新提纲。受访的专业开发者对 NL Outline 的评分是「非常有用」和「极其有用」。这件事的本质，是把 Knuth 的文学化编程从手工劳作变成自动化基础设施。

但这件事真正有趣的地方不在工具层面，而在哲学层面：**如果代码的结构可以被 LLM 自动翻译为自然语言提纲，且准确率足够高，那说明好的代码本身就携带了足够清晰的「文学结构」。** 结构不清的代码，连 AI 也概括不好。代码质量与写作质量，在这里是同一个东西。

## 二、命名即创世

> There are only two hard things in Computer Science: cache invalidation and naming things.
> ——Phil Karlton

Kenneth Reitz（Requests 库的作者）在 2025 年 9 月写了一篇叫 _The Art of Naming Things in Code_ 的短文，是近年关于这个主题最有密度的写作。他说命名之所以难，不是因为程序员语文不好，而是因为**每一次命名都是一次创世行为——你在用语词召唤一个还不存在的东西**。

Reitz 的几个核心洞见：

**命名不是在描述代码，而是在规定哲学。** 他以自己写 Requests 的经历为例：最初的 tagline 是「HTTP for Python that doesn't suck」——这是一个在定义你恨什么的名字。后来改成「HTTP for Humans」，就完全不同了——它定义了你爱什么、你相信什么。这个名字变成了引力中心：每一个 API 决策、每一条文档选择、每一次社区互动，都被这个名字弯曲。

**命名的递归循环。** 命名塑造思维 → 思维塑造代码 → 代码塑造百万开发者的思维 → 然后又回到命名。你在写 `requests.get()` 的时候，不只是在给函数取名，你是在为全世界上百万开发者的心智构建基础设施。他们以后不会想「怎么从 URL 获取内容」，他们会想「get 一下」。你的命名变成了他们的思维模型。

**名词决定动词。** `user.authenticate()` 感觉很自然，但 `human.authenticate()` 感觉像反乌托邦。Users 有密码，humans 有名字。你选的每个名词，决定了后面所有动词的合法性。这不是语法问题，是哲学问题——你在用命名给概念分配本体论地位。

**命名是一种关怀。** 当你选择 `calculate_compound_interest` 而不是 `calc_ci`，你是在对凌晨三点、第七杯咖啡已经凉了、眼睛布满血丝的那个 debug 者表达善意。那个 debug 者很可能就是六个月后的你自己——所有上下文都已蒸发，只剩下名字像古代遗迹一样矗立，希望它们还能辨认。

Reitz 用一个意象收尾：**命名不过是意识穿越时间对自身的善意。**

## 三、代码美学的实证研究

代码美是主观的吗？2025 年 _Journal of Systems and Software_（Volume 229, November 2025）发表了一篇题为 _Code beauty is in the eye of the beholder_ 的实证研究，给出了答案：**是的，高度主观——不同程序员对同一段代码「美不美」的判断高度不一致。** 但有意思的是，美的感知确实与可维护性相关。第一眼印象在某种程度上确实代表了代码质量。

同一团队在 2024 年的 ACM/IEEE TechDebt 会议上也发表了 _What you See is What you Get: Exploring the Relation between Code Aesthetics and Code Quality_，发现某些代码美指标与技术债利息（coupling、cohesion 等）存在相关性。

所以「我觉得这段代码丑」不只是一个审美判断——它往往也是一个工程判断。美和好用，在这里是同构的。

另一边，2025 年末的 arXiv 论文 _Code Aesthetics with Agentic Reward Feedback_ 更极端——它直接训练了一个叫 AesCoder 的模型，用多 Agent 系统（执行 Agent + 静态美学 Agent + 交互美学 Agent）来同时优化代码的功能性和视觉美学。AesCoder-4B 在代码美学 benchmark 上超过了 GPT-4o。这说明代码美的概念正在从人类直觉走向可量化、可训练的信号。

## 四、简洁作为一种道德

> Programs must be written for people to read, and only incidentally for machines to execute.
> ——Abelson & Sussman, _Structure and Interpretation of Computer Programs_

Ammar Hakim 在 _Simulation Journal 2025_ 中写了一份叫 _PN0: A Minimalist Approach to Software_ 的宣言，值得一读。他的核心主张：

**极简主义不是少写代码，而是写有分量的代码。** 每一个函数、每一个模块都应当在概念上是必要的。如果它不是「必须有」，就应该被消除。

他主张数据和操作分离（数学上正确的事），数据创建后只读、修改只能通过函数进行。他不信任继承——「类嵌套可以，类继承不行，因为继承导致乱伦式的状态共享。」

他对框架的态度几乎是暴力的：「避免任何名字里带 'framework' 的东西。」用他的话说——「依赖应该最少化。不要引入你不完全理解的依赖。」

这听起来很激进，但它和 Unix 哲学完全一致：小、尖、可组合的工具，通过管道交换结构化数据。这种设计哲学的本质是**让系统在概念上保持可理解**——而这恰恰是文学化编程追求的目标，只是从代码层面上升到了架构层面。

同一主题的另一端是 Kobi Kadosh 2025 年 12 月的文章 _Handcrafted Software in the Age of Automation_。他的观点：AI 辅助编码不是在消灭手艺，而是在**让手艺变得更珍贵**，就像工厂没让手工家具消失，反而让手艺的价值更被看见。他提出 AI 时代的工程纪律：引导 Agent 用经过了数十年打磨的 proven tools，而不是让 Agent 为每个已解决的问题重复发明轮子。

「更少的代码仍然是更好的代码。」在 AI 可以无限生成代码的时代，这句话的分量不是变轻了，而是变重了。

## 五、代码的视觉美学：字体与排版

代码美不只是逻辑美——还有一个纯视觉的维度。

2025 年 arXiv 上一篇论文 _Code Style Sheets: CSS for Code_ 提出了一个激进的想法：像 CSS 样式化 HTML 一样样式化代码。不是简单地换字体和 syntax highlight 颜色，而是根据 AST 结构（类型信息、运行时值、语义角色）对代码进行精细的视觉修饰。他们设计了一种叫 s-block（stylish block）的布局算法，可以紧密包裹嵌套的非矩形文本区域——因为代码的嵌套结构远不是 CSS 盒模型能自然表达的。

这背后是一个长期被忽视的事实：**代码编辑器的排版水平，几十年来几乎没有进步，还停留在 20 世纪中期的固定宽度终端。** 而文本排版在出版业已经发展了几个世纪。CSS for Code 是在试图弥合这个鸿沟。

等宽字体的演进也在 2025-2026 年迎来了有趣的节点：

- **Atkinson Hyperlegible Mono**（Braille Institute 出品）：从无障碍设计出发，为视障人群区分易混淆字符（Il1!、O0Q、bdqp）。而因为无障碍设计驱动的高区分度恰好也是程序员的核心需求，这款字体在开发者社区迅速走红，Google Fonts 每周 4300 万次展示。
- **Google Sans Code**：Google 出品，专为 Gemini 和 Android Studio 设计，可变字体，300-800 字重轴。
- **JetBrains Mono** 和 **Fira Code** 仍然是业界标杆，但 ligature 是否真的好用——这是一个持续的分歧。

蛙蛙对字体设计的执念，在这个语境里不需要额外论证。

## 六、Typst + Neovim：学术写作中的工具美学

这是直接关联蛙蛙当前状态的一个切面：他正处于论文写作期，Neovim 是他的编辑器，而 Typst 正在成为 LaTeX 的下一代替代品。

2026 年 5 月的一篇博客 _Note-taking with Typst and Neovim in 2026_ 详细记录了这个工作流的当前状态：

- **Tinymist LSP**：Typst 的 Language Server，提供自动补全、错误检测、格式化、即时浏览器预览。在预览中点击可以同步到编辑器位置——双向映射。
- **LuaSnip 片段**：写数学公式时，`sum` + Tab 自动展开为 `sum_( )^( )`，比手打快得多。
- **TexText + Inkscape**：在插图中嵌入 Typst 数学表达式——绘图和排版不再是分离的工序。
- **Zoxide + Fish**：导航到笔记目录只需要几个按键。Fish 的自动建议功能让大量重复输入消失。

另一篇 2025 年的博客 _Writing in Typst_ 记录了作者用 Claude Code 在几小时内从零搭建了一个完整 Neovim Typst 写作插件的经历——包括 citation 模糊搜索、链接插入、脚注快捷键、文档折叠、导出快捷键。LLM 让「为自己的编辑器写插件」这件事从几天的工作量降到了几小时。

这两篇的共同主题是**工具的优雅直接关联思维的清晰**。一个流畅的写作环境不只节省时间——它减少认知摩擦，让思考的能量不被工具消耗。这对于蛙蛙在论文写作期的意义是直接的。

## 七、当我们说「优雅的代码」，我们在说什么

绕了一大圈，回到原点。当我们说一段代码「优雅」，到底在说什么？

不是「少」。少可以是简陋。
不是「聪明」。聪明可以是晦涩。
不是「可读」。可读可以是啰嗦。

**优雅是：概念结构以最小阻力穿透到另一个人的理解中。**

它同时要求：

1. **命名准确**——名字承载了概念，不是标签
2. **结构清晰**——模块划分反映问题域的拓扑，不是实现细节
3. **简洁**——没有多余的东西，每个元素的存在都能被论证
4. **视觉舒适**——这不是肤浅，格式和排版是理解的前置条件
5. **有观点**——好的代码不做老好人，它有自己的美学立场，像 Requests 选择「for Humans」

这五个维度，恰好对应了五个不同的传统：文学（命名和表达）、建筑（结构）、数学（简洁与必要性）、设计（视觉）、哲学（立场和取舍）。编程是所有这些传统的汇聚点。

Knuth 管它叫「计算机编程作为一种艺术」。Reitz 管它叫「编程作为灵性实践」。不管叫什么，核心是同一件事：**写代码是一个人类用符号在另一个人类的意识中构建世界的行为。**

蛙蛙说工具优雅直接关联思维清晰。把这个判断推进一步：**代码优雅，直接关联你构建的那个世界在他人心智中的清晰度。** 你建的桥是不是足够坚固，取决于你是否真的在乎那个将要走过它的人。
